# CLAUDE.md — studio

Студия `https://studio.example.com` — многопользовательское приложение (PWA) с учётками, историей и
разделами чат · фото · видео, плюс пакетные скрипты для Windows и Linux — клиенты API картинок и
видео LLM-шлюза srvllm. Что умеет и как пользоваться — [README.md](README.md); спека —
[docs/superpowers/specs/2026-10-19-studio-pwa-design.md](docs/superpowers/specs/2026-10-19-studio-pwa-design.md).
Репозиторий — **приватный** (хосты LAN): `origin` — `git.example.net/xadmin/studio`;
Gitea — серверное pull-зеркало. Публикация и выкладка агента используют только этот контур.
Решение владельца 2026-11-04: `cld` он обновляет вручную, когда нужно. Агент не проверяет,
не синхронизирует и не пушит `cld`; его состояние не является условием выкладки.

## Устройство

Создание истории защищено `app/operations.py`: `auth.guard` захватывает поколение до чтения тела
запроса, фоновые задания наследуют его. Очистка истории и отключение/удаление учётки через
`history`/`admin` закрывают поколение; `operations.check` после ожиданий и перед вставкой запрещает
позднее сохранение, даже после повторного включения учётки. Начатое во время очистки также
отклоняется: `409 history_changed`, отключённая/удалённая учётка — `401 login`. Файлы media
откатываются через очередь удаления; принятый шлюзом поздний ролик снимается у шлюза по обычному
контракту отмены. Проверки — `tests/test_creation_barrier.py` и гонки в `test_media.py`/`test_chat.py`.

`claude_code.ask` повторно проверяет живую незапертую сессию после ожидания любого ответа моста,
включая отказ: `409 closed` без приватного результата. PDF повторяет проверку после рендера.
Web Push выбирает только живые сессии активной учётки и перепроверяет получателя перед каждой отправкой.

Прямые уведомления ntfy — `app/ntfy.py`, схема 30: `ntfy_devices` привязаны к digest сессии,
каскад от `sessions` и учётки. Прежние `ntfy_settings` — только шаблон параметров, без отправки.
Миграция сохраняет сервер/токен, назначает разные темы и выключает ntfy у всех устройств;
новая сессия тоже всегда начинает с выключенным ntfy. Общая тема не назначается новому устройству.
«Настройки → Прочее → ntfy» (`ntfy-settings.js`): HTTPS-сервер из административного allowlist,
тема, необязательный токен, включение, сохранение/проверка/сброс. `GET/PUT/DELETE /api/me/ntfy`,
`POST /api/me/ntfy/test` — только текущая сессия, CSRF и блокировка по общим правилам; сброс
меняет только её настройки, тест шлёт только её теме. Токен шифром
`security.encrypt`, наружу только `has_token`; отсутствующий токен сохраняется лишь у прежнего
сервера, пустой удаляется. Доставка — JSON POST в корень ntfy через `upstream.request` (DNS pinning,
публичные адреса имени, TLS, без redirect, 10 с), без переписки, с `click` на свой origin.
`push.notify_later` отправляет Web Push и ntfy независимо; события мостов и заданий общие.
`GET /api/jobs.push` учитывает ntfy только текущей сессии, чтобы её локальные уведомления не дублировались.
Доставка — включённым непросроченным сессиям активной учётки, с дедупликацией server/topic и
независимой обработкой отказов устройств. Выход/истечение сессии прекращают её доставку.
Клиенты ntfy получают всё из своей темы: для физического разделения доставки темы должны отличаться.
Ссылка `ntfy://` в настройках открывает подписку на сохранённую тему этого устройства. Тесты: `tests/test_ntfy.py`,
`tests/test_ui_ntfy.py` (integration, 320/1280).
`ntfy` не импортирует `upstream` при загрузке: цепочка main → bridge → push → ntfy иначе
замыкает connections/upstream до объявления `UpstreamRefused`. На Debian Python 3.13 аннотация
`connections.refused` вычисляется сразу, а локальный Python 3.14 скрывал этот сбой. Проверка
холодного импорта — `test_ntfy_import_does_not_start_the_connections_cycle`; после изменения
цепочки импорта дополнительно проверить `import main` на Python хоста до перезапуска службы.

Часовой пояс — `users.timezone` (схема 27), по умолчанию `Europe/Moscow` у новых и прежних учёток.
`GET/PATCH /api/me` читает/сохраняет IANA-пояс с проверкой `zoneinfo` (`tzdata` нужна и на Windows).
«Настройки → Прочее → Часовой пояс» сохраняет выбор для всех устройств; `app/static/js/time.js`
форматирует все даты/время интерфейса и считает календарные сутки для «Сегодня»/«Вчера» с учётом
переходов часов. Метки API/базы остаются секундами Unix, длительности не зависят от пояса.
Фильтры дней `/api/search` тоже используют пояс учётки, включая сутки на 23/25 часов.
`chat.with_date` берёт тот же `users.timezone` для календарной даты в запросах серверу,
браузеру и Cleaner; Москва остаётся умолчанием, Unix-метки и длительности не меняются.
Проверки — `test_ui_timezone.py`, `test_ui_project_summary.py`, `test_profile_admin.py`, `test_foundation.py`.

С 0.12.0 `hello.desktop: true` объявляет пульт рабочего стола, `app/desktop.py` и
`code-desktop.js/css`. Разрешение `Config.desktop_enabled` по умолчанию false; только локальный

переподключения. Выбор сохраняется при перезапуске. У HTTP/протокола/CLI нет изменения разрешения.
Все операции требуют своей сессии, обычного PIN и CSRF для POST; токен одного сеанса только в памяти.
`desktop_status/start/frame/input/clipboard/stop` — §14 протокола; отдельные HTTP-запросы с одним
кадром в полёте, без очереди изображений. Сервер фильтрует ответы и повторно проверяет сессию после
ожидания моста; данные не сохраняются. Блокировка шлёт `desktop_close` без сброса обычного PIN.
Мост отзывает управление при локальном выключении/обрыве/10 с без запросов; `desktop_native.py`
в одном рабочем потоке проверяет WTSActive/Default input desktop, захватывает JPEG, посылает SendInput,
обменивается текстом CF_UNICODETEXT; своим окнам ввод запрещает. Активный пульт удерживает обновление.
С 0.13.1 `desktop_status.resolutions` объявляет варианты длинной стороны JPEG 640–2560 px;
`desktop_frame.max_edge` необязателен, по умолчанию 1600. Сервер опускает поле при значении 1600
для старого моста; без списка разрешений UI оставляет только 1600. `code-desktop` занимает всю
ширину, высота кадра следует его пропорциям; Touch — прямой ввод, Мышь — относительный тачпад,
видимый курсор, ЛКМ/ПКМ, удержание ЛКМ и прокрутка. Смена режима/монитора и отмена жеста
отпускают ввод; старый кадр после смены монитора/качества не показывается.
Проверки: оба `test_desktop.py`, `agent/tests/test_desktop_native.py`, `tests/test_ui_desktop.py`,
`agent/tests/test_window_integration.py`. Настоящие экран/ввод/буфер требуют ручной приёмки после
локального включения владельцем; синтетические и браузерные тесты этого не подтверждают.

С 0.10.0 `hello.agent_version` сообщает версию самого моста, `hello.agent_update` объявляет обновление.
`GET /api/agents` добавляет `agent_version`, `agent_update`, `latest_version` (последняя — из опубликованного ZIP).
В дереве компьютеров после имени идут версия, круглая кнопка обновления с двумя стрелками, сведения
и подключение к рабочему столу (монитор со стрелкой), без видимой метки PIN и подписи о новой версии.

этапы и ошибки запрошенного обновления. `POST /api/code/agents/<aid>/update` передаёт только серверные
version/sha256/size. Кнопка запускает обновление доступного совместимого моста; в остальных случаях
скачивает установщик Windows, включая старые/offline/уже актуальные мосты.
`GET` того же адреса — стадия. Обе команды требуют своей сессии, CSRF для POST и открытия PIN.
`GET /api/agent/package` без браузерной сессии проверяет Bearer действующего устройства активной учётки.
`agent/studio_agent/updater.py` скачивает только с настроенного HTTPS-сервера без redirect, проверяет ZIP,
готовит отдельную копию/venv и ждёт `live()` всех Runner и окончания просьб канала. Новые изменения/ходы
блокируются; работающие задания продолжаются. Самостоятельный `update_helper.py` ждёт штатного выхода,
запускает новую копию, сохраняет настройку автозапуска; ранний сбой запуска возвращает прежнюю копию.
Ключи/PIN/переписки не входят в пакет или план. Старые версии требуют однократной ручной установки 0.10.0.
Проверки: `test_agent_update.py`, `test_ui_agent_update.py`, `agent/tests/test_updater.py`.

фоновые проверки скрывают данные закрытого/offline компьютера. Обновлять мост для этого не требуется.
Проверки — `test_code_activity.py`, `test_ui_agent_attention.py`, миграция в `test_foundation.py`.
Месячный лимит не выдумывается, неизвестные окна — available=false; Claude OAuth usage недокументирован.
Круг контекста: <50 зелёный, 50 жёлтый, 70 оранжевый, 90 красный. `code-context.js` открывает подробности
сессии по нажатию: окно, занято/свободно, расход, модель/права/id. Мост 0.7.4 добавляет необязательный
`context.usage`: накопленные счётчики Codex и главной сессии Claude (SDK-история без дублей по message.id).
Справа `code-usage.js` показывает остаток недели сразу при открытии чата, по нажатию — остальные лимиты.
`code-git.js::gitLevel` задаёт красный/жёлтый/зелёный цвет Git в шапке и боковой панели; неизвестное — нейтральное.
В шапке порядок: статус Git → Git → Файлы → Чат. Нажатие статуса открывает окно с четырьмя действиями:
коммит; коммит и пуш; коммит и пуш во все Git; коммит, пуш во все Git и деплой. Во вкладке Git этих кнопок нет.
Каждое действие проверяет diff и тесты и создаёт коммит при наличии изменений; пустые коммиты не создаются.
Действие возвращает в выбранный чат проекта и отправляет задание текущему помощнику, сохраняя черновик.
Без выбранного чата автоматически создаётся чат первого доступного агента по приоритету учётки; при подготовке действия и занятости чата
кнопки недоступны. `code.js` сверяет список чатов при открытии окна действий и перед выполнением действия.
Окончание задания обновляет Git и сводку проекта; `gitinfo.status` без upstream добавляет unpushed по локальным refs.
`appearance.js` и ранний `theme.js` применяют размер текста 85–150% и масштаб 50–100% с шагом 5% из localStorage
(только настройки вида). `code-tabs.js` сохраняет узлы; `code-chat.js` кэширует до 12 историй только в памяти
с обязательной сверкой при возврате, сбрасывает историю по closed/done. Серверная история и тексты не кэшируются
на диске браузера. `code.js` держит в памяти списки названий 20 последних проектов с ключом учётка/компьютер/проект;
«+» показывает сохранённый список сразу и обновляет в фоне, одновременные обновления объединяет.
`code-sessions.js` ищет по словам названия (регистр и е/ё не различаются), сохраняет запрос при обновлении;
длинные названия ограничены двумя строками с полным текстом в title. Браузерные проверки — `tests/test_ui_agent_controls.py`.

## Правила

- **Приватность — контракт, а не пожелание. История — в базе и на шаре, в журнал — ничего.**
  Промпты, ключи, пароли, тексты сообщений и документов, картинки, ролики и имена файлов в журнал
  не пишутся (uvicorn с `--no-access-log`, журнал — только события с id). Новый код это не ломает
  (сторожат тесты журналов разделов).
- **Анонимны только** `/health`, `/login` (страница и вход), `/logout`, `/robots.txt` и оболочка
  PWA: `/static/*`, `/manifest.webmanifest`, `/sw.js`, `/offline.html`, значки из корня
  (`/apple-touch-icon.png`, `/apple-touch-icon-precomposed.png`, `/favicon.ico`); `/` без сессии уводит на
  вход, всё `/api/*` — через `auth.guard` (сессия + CSRF у изменяющих запросов). Страницы отвечают
  и на HEAD. Два входа моста Claude Code: `/api/agent/enroll` — анонимен (`auth.OPEN_API`; `POST` — это и есть
  вход логином и паролем — свои паузы и счёт неудач `/login`, `DELETE` — отвязка ключом устройства в заголовке,
  чужой `Origin` — 403); `/api/agent/link` — WebSocket,
  вход ключом устройства (`Authorization`) в самом обработчике: `guard` — HTTP-middleware и WebSocket не видит.
- Защита входа от перебора — паузы (на пару «логин + адрес» и на адрес); растущая задержка ответа
  на неверный пароль параллельные попытки не тормозит — на неё не полагаться.
- **Пользователь видит только своё**: каждый запрос к истории, файлам и подключениям — с
  `user_id` сессии; панель администратора чужую историю не показывает.
- **Исключение из правила списка разрешённых адресов** («Устройство» → подключения) — только адреса,
  зашитые в `web.py` (`api.exa.ai` и YouTube через yt-dlp) и в `push.py` (службы push, ниже). Первые не выбирают ни пользователь, ни модель:
  адрес страницы уходит в Exa данными, сервер по нему не ходит, и `read_page` берёт только адреса из
  сообщений и документов диалога или из `results[].url` поиска (иначе — шаг-ошибка, в Exa ничего: страница
  или выдача не уведут переписку на чужой сайт краулером Exa; сравнение — `web.norm`, а в Exa уходит адрес, как
  он записан там, без фрагмента — вариант модели не канал наружу); yt-dlp получает только канонический
  адрес из id (у него общий извлекатель — чужой адрес, в том числе внутренний, сервер прочитал бы), и
  только ролика, чей id совпал с id адреса из сообщений и документов диалога или из `results[].url`
  поиска (`web.youtube_id` от адресов `known`, любая форма — watch, youtu.be, shorts, live, embed, music,
  m.; иначе — шаг-ошибка `NOT_KNOWN`, yt-dlp не зовётся: id из 11 знаков, составленный моделью, — тот же
  канал наружу, что и адрес страницы), с урезанным окружением (без `STUDIO_DATA_KEY`) и не больше двух сразу.
  Наружу — только при `chats.web = 1`: иначе в запросе к модели нет `tools`, Exa и yt-dlp не зовутся; в
  Exa — только `query` (до 500 знаков) / `url` (до 2048) из вызова модели, не переписка (сторожат
  `test_chat_web.py`, `test_web.py`). Адреса подписок push — только службы `push.HOSTS` (https, без порта и
  пользователя, до `push.ENDPOINT_MAX`); адрес присылает браузер, сервер шлёт туда лишь зашифрованное (RFC 8291)
  уведомление без содержимого чатов — «<имя компьютера> · <имя проекта>: <повод>» (`push.allowed`, сторожит `test_push.py`).
- **Ключ Exa — свой у учётки**, `users.exa_key` шифром `security.encrypt` (как токены; смена
  `STUDIO_DATA_KEY` — вводят заново, `web.NO_KEY`). В браузер, ответы API, выгрузку и журнал не уходит:
  `GET /api/me` — только `exa_key: true|false`; при сохранении запросом к Exa не проверяется (тратил бы
  баланс). «Удалить всю историю» его не трогает — настройка, как пресеты.
- **Путь к службе один — Apache debian.** Служба слушает только unix-сокет `/run/studio/web.sock`
  (каталог `0750 studio:www-data`) и потому верит последнему элементу `X-Forwarded-For`. Порт TCP
  не открывать: счёт попыток входа подделывался бы заголовком.
- Секреты — vault `local-config/secrets/vault.env`; в репозиторий — никогда. Значения едут на хост только
  потоком stdin (`grep … | ssh`), не в argv и не в вывод. Скрипты в репозитории без ключа
  (`$EmbeddedKey = ''`, `EMBEDDED_KEY = ""`, сторожат тесты), копии с ключом — `*.local.ps1` и
  `*.local.py`, в `.gitignore`.
- `client/*.ps1` — UTF-8 **с BOM** и CRLF (PowerShell 5.1 без BOM читает CP1251).
- `client/*.py` — Linux-версии тех же скриптов: UTF-8 без BOM, LF (иначе shebang не сработает),
  Python 3.8+ без сторонних пакетов. Правка поведения — в обеих версиях сразу: общие сценарии
  `test_studio_{batch,video}_client.py` гоняют обе (`-PromptsFile` у PowerShell = `--prompts-file`
  у Python, это и сверяют).
- `deploy/*` — LF (`.gitattributes`): `\r` systemd принял бы за часть пути, bash — за часть команды.

## Выкладка

    bash deploy/deploy.sh                    # HEAD → debian, install.sh, проверка через Apache
    bash deploy/deploy.sh --new-secret       # заново положить STUDIO_DATA_KEY из vault
    bash deploy/deploy.sh --create-admin     # первый администратор и его подключение «srvllm» из vault

Выкладывается закоммиченный HEAD (`git archive` частей `app deploy requirements.txt`); грязное
дерево выкладываемых частей и `agent/` — отказ. С ним едут установщик EXE и ZIP обновления моста:
`git archive --format=zip --prefix=studio-agent/ HEAD:agent` → `.incoming/agent/studio-agent.zip`, строка
`==> мост <хеш>` того же коммита студии. До первого SSH `deploy/build-agent-installer.ps1` собирает
`studio-agent-setup.exe` из этого ZIP и `deploy/agent-installer.cs` того же HEAD (штатный csc .NET Framework Windows).
`GET /api/agent/download` отдаёт EXE браузеру, `/api/agent/package` — ZIP действующему мосту.
Нет моста в HEAD или он грязный — отказ до копирования кода. `install.sh` без ZIP или EXE —
отказ до подмены; `agent` переезжает в `SWAP` с кодом, и откат `.previous` возвращает оба файла.
Ключ данных при первой установке (в `studio.env` нет `STUDIO_DATA_KEY=`) едет сам.
`--create-admin` берёт из vault `STUDIO_ADMIN_LOGIN`, `STUDIO_ADMIN_PASSWORD`,
`GATEWAY_KEY_OWNER_IMAGES` и через `install.sh --admin-stdin` отдаёт в `manage.py create-admin`
(`systemd-run --pipe` от `studio` с окружением юнита); повтор безопасен, новый пароль гасит сессии.
`install.sh` до подмены кода собирает новую среду Python рядом (`.incoming/.venv`; только если
сменились `requirements.txt` или `python3` — штамп `.venv/.studio-requirements`), переносит её на
место вместе с кодом, держит прежние код и среду в `.previous` до ответа `/health` от www-data
через сокет, ставит юниты копии базы и включает таймер. Отказ `systemctl restart` и молчание `/health`
идут одним путём `service_failed` — status, журнал и строки отката, без автоматического отката; таймер
копии базы, который не включился, — ошибка с кодом не 0 (служба уже обновлена). Перенесённая среда — с чужим shebang в
`bin/`: всё запускается `.venv/bin/python` (`-m uvicorn`, `-m pip`, `manage.py`), не `bin/<скрипт>`. Перезапуск ждёт
открытые потоки чата не дольше 10 с (`--timeout-graceful-shutdown`, `TimeoutStopSec=30`);
недописанное помечают `chat.recover()` / `images.recover()` / `ocr.recover()` / `translate.recover()` при старте. Каналы мостов Claude Code остановка закрывает 1012 (`bridge.stop`): мосты
переподключаются сами, ходы на машинах идут дальше; мост ≥ 0.7.1 сохраняет оставшийся срок PIN компьютеров. Смоук —
`https://studio.example.com/health`; живая приёмка — `tests/test_studio_upload_live.py` (ниже).

Windows-мост после выкладки сервера перезапускать не нужно. Активный мост нельзя завершать (Stop-Process/kill)
из выполняемого им задания: вместе с ним прервётся исполнитель. Мост обновляют после завершения заданий
и явного выхода в трее; установщик ≥ 0.7.2 отказывает до копирования файлов, если эта копия моста запущена.

## Ловушки

- `ProxyPass` — на имя `studio-backend`, не `localhost`: mod_proxy подбирает воркер по префиксу
  URL, и чужой корневой `|http://localhost/` увёл бы запросы в свой сокет.
- `ProxyPass /api/chats/` (600 с, `flushpackets=on`, `no-gzip`) — раньше общего `ProxyPass /`:
  берётся первое совпавшее правило, а поток чата не должен копиться в буфере и рваться по 120 с.
  Так же `ProxyPass /api/videos` (330 с): создание ролика отвечает после шлюза — исходник на шару,
  задание, поиск потерянного ответа и снятие у шлюза подряд дольше общих 150 с.
- `LimitRequestBody` vhost не меньше пределов службы (документ и картинка ролика — 20 МиБ, фото
  с маской 2×10 МиБ) — сверяет `test_apache_lets_through_the_largest_body_the_studio_accepts`.
- SQLite — только на локальном диске: на CIFS он портится. Копия базы на шару — готовым файлом
  (`journal_mode=DELETE`), а не живой базой.
- `studio-backup.service` — с теми же `User`/`Group`/`StateDirectory`, что у службы: другой
  `Group` у того же `StateDirectory` systemd перевёл бы владельца каталога базы.
- Отмена задания запрос к шлюзу не обрывает (LiteLLM обрыв дальше не передаёт): задание ждёт
  конца, выбрасывает картинку и само освобождает карту (`release_after_cancel`).
- Аренда модели картинок держит карту 600 с простоя, и другая модель её не вытесняет: без
  release FLUX после Lustify ждал карту 300 с и получал 503 (приёмка 2026-10-20). Поэтому
  `images.generate` перед запросом отпускает другую модель; тесты считают и эти release.
- Освобождение карты после отмены идёт подключением учётки (токен читается из базы): удаление
  учётки ждёт её заданий (`images.settle_user`, до `SETTLE_SEC`), иначе каскад унёс бы токен.
- Список роликов шлюза (`GET /slot/videos`) общий для всех ключей: студия читает его только для
  ролика, ответ на создание которого потерялся, и только если seed выбрала она сама
  (`videos._adopt`: случайный 32-битный seed — единственный признак своего, плюс параметры и
  промпт). Seed пользователя (скрипты и другие учётки ставят те же 42) ничего не доказывает:
  тогда список не читается, ответ — «ролик мог начаться» (`LOST_MANUAL`). Не ослаблять: чужое
  задание студия скачала бы в ленту и сняла у шлюза.
- HTTP-клиент службы (`state.make_http`) один на всех пользователей и cookie ответов не хранит
  (`CookieJar` с политикой без доменов, передан самой банкой: `httpx.Cookies(...)` скопировал бы её
  без политики) — иначе cookie сервиса из запроса одного уходила бы с запросами других к тому же хосту.
- Наблюдатель роликов не ждёт подключения по очереди: ролики каждого подключения — своей
  задачей (`videos.WATCHING`, не больше `POLL_MAX`), не ответивший по сети шлюз — на паузе
  `PAUSE_SEC`, mp4 целиком — за `FETCH_SEC`. Остановка гасит задачи вместе с `_watch`.
- Освобождения слотов `asr` и `tts-qwen` у шлюза нет: перед расшифровкой и озвучкой студия
  освобождает модели картинок и gemma-abl (`speech.free_card`), а на 503 ждёт и повторяет
  (`RETRY_SEC`, до `WAIT_MAX_SEC`). Отмена обрывает только свой запрос — WhisperX дослушает запись.
  Голосовой ввод WhisperX — так же, но в пределах своего бюджета (`dictation.BUDGET_SEC`, затем 504).
- Слот `ocr` (6656 МиБ) не помещается рядом ни с gemma-abl, ни с comfy и держит карту арендой 900 с:
  перед первой страницей документа — `speech.free_card`, после каждого документа (готово, ошибка, отмена —
  звал он шлюз или нет) и после отмены ждущего — `ocr._settle`: `POST <адрес>/pages/ocr-release {}` каждому
  шлюзу из `ocr.LEASED` (`ocr.release`; 409 `slot_busy` — повтор через `RETRY_SEC` до `RELEASE_RETRIES`),
  если в студии не идёт и не ждёт другое распознавание. Решает студия, а не документ: последним может
  кончиться документ, что шлюз не звал (пустые страницы, отмена до первой страницы). Запись `LEASED`
  снимает только удачный release, и только если она та же и новый документ не начался; неудачный оставляет
  её концу следующего документа. Без release
  Lustify и gemma-abl ждали бы 15 минут. Отмена идущего документа запрос страницы не обрывает: раннер
  дожидается ответа, выбрасывает его и только потом освобождает карту (`stop_user` обрывает сразу, release —
  фоном: шлюз ещё считает оборванную страницу, 409 и повтор). Из обработчиков HTTP (отмена ждущего,
  `stop_user`) release — фоном, `ocr.settle_later` (`ocr.SETTLING`, гасит `ocr.stop`): ответ шлюза не ждёт.
  Ход чата со сканом зовёт модель только после `ocr.idle` — раннер уже освободил слот и release фоном нет:
  итог документа пишется раньше release, и gemma-abl иначе ждала бы карту под арендой `ocr`. Перевод — так
  же; снимок перевода распознаётся вне раннера, под `ocr.borrowed`: пока он идёт, он в `ocr.EXTERNAL`, и
  release другого распознавания его не оборвёт.
- Имя файла записи едет заголовком `X-Studio-Name`, а не строкой запроса: строку пишет журнал Apache.
- Перевод промпта («EN», `POST /api/images/translations`) идёт маршрутом описания

- Из LAN запрос на публичный адрес приходит с роутера 10.77.1.1 (петля): для него пауза входа —
  только на пару «логин + адрес» (`config.hairpin_ip`), иначе запирался бы весь дом.
- Блокировка на телефоне — 423 `screen_locked`, пауза после неудач — 429 `locked`: не путать (и

- Варианты passkey (`/api/lock/challenge`, `/api/passkeys/options`) готовятся до нажатия, а

  пока идёт вызов устройства, новых не готовить — новый заменил бы подписываемый (403).
- Шторка и экран блокировки — `<dialog>` через `showModal()`: иначе открытое окно просмотра

- `seen` сессии — только по отметке `POST /api/lock/alive`, а не по любому запросу: опросы разделов
