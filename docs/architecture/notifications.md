# «В работе», Web Push, ntfy

## «В работе» (`jobs`)

`jobs` — свои идущие и готовые за час задания всех разделов: только база и память модулей, к шлюзу не ходит.
Страница — `jobs.js`: значок и панель, опрос `GET /api/jobs` и уведомления (локальный запасной вариант через
`showNotification`, флаг устройства `studio-notify`); нажатие на уведомление — `notificationclick` в `sw.js` (окно студии, которым работник не управляет — после
жёсткой перезагрузки, — `navigate()` отклоняет: тогда `focus()` и адрес сообщением, новая вкладка — только если и фокус
не удался); разделы
переходят к записи по `?id=` и зовут `jobs.js::kick` после запуска. У идущих строк — `cancel` (`jobs.CANCEL`; у чата —
`/api/chats/<id>/stop`), в панели «Отменить» (адрес проверяется регуляркой); закрытый раздел — 423.

- «Готово за час» на странице (`jobs.js` `take`): строка того же id с более поздним `finished` — новый итог повторённого
  задания (скан, перевод, озвучка заново берут прежний id): заменяет прежнюю и уведомляет; id, снова идущий, из готового
  уходит. Открытие панели опрашивает без `since` и берёт готовое целиком — записи, удалённые в разделе, уходят.
- Ответ чата через сервер (`chat.StreamTask`) по готовности или ошибке (не «стоп» и не остановка службы) попадает в
  `chat.ANSWERED` (память процесса, `chat.ANSWERED_SEC`) — строкой «Готово за час» (`jobs._chat_done`, только пока есть
  диалог и сообщение) — и уведомлением `push.chat_answered` («ответ готов», адрес `chat/<id>`).
- Скан вложения чата (`scans.origin = 'chat'`) push не шлёт (`push.job_finished`): о нём скажет ответ.
- Страница на экране (F6): опрос шлёт `visible=1|0` (`jobs.js`: видимость; скрываясь — сразу опрос), `push.screen`
  держит отметку `push.ON_SCREEN` не дольше `push.SCREEN_SEC` (15). Готовность заданий и ответов (`notify_later`
  `quiet=True`) таким сессиям не идёт ни push, ни ntfy (`push.on_screen`); события «Агентов» и служебные — как раньше
  (у «Агентов» своё правило — `bridge.watching`). Служебный работник показывает каждый пришедший push (Safari
  отзывает подписку за «тихие»), поэтому решает сервер.

## Web Push (`push`)

Ключ VAPID (P-256) — `settings` `vapid` шифром `STUDIO_DATA_KEY`, тело — RFC 8291 aes128gcm, подпись JWT ES256;
`GET/POST/DELETE /api/me/push`, флаг устройства `studio-push:<id учётки>` (`push-sync.js` `pushFlag`; прежний общий
`studio-push` переходит первой учётке, что его прочтёт); адреса — только `push.HOSTS`. Поводы «Агентов» —
`bridge._push` (подробно — [agents.md](agents.md)); задания разделов — `push.job_finished` (первое сохранение итога,
отмена — тишина; название «Студия», текст — только повод, адрес `<раздел>?id=<id>`; скан перевода и отправленного
хода чата — без своего, `ocr.SERVED`). Web Push выбирает только живые
сессии активной учётки и перепроверяет получателя перед каждой отправкой.

- У сессии одна подписка: новый `POST` удаляет прежние адреса этой сессии. `GET /api/me/push.endpoint` — первые 16 hex
  SHA-256 адреса подписки.
- `sw.js`: на 423 подписка остаётся, окнам — `{push:'resync'}`; `push-sync.js` (зовёт `app.js::enter`) сверяет признак
  с подпиской браузера и досылает через `api.js` (под замком ждёт отпирания); `pushsubscriptionchange` переподписывает.
- Подписка живёт с сессией (каскад `push_subs` от `sessions`). Флаг стоит, разрешение и подписка браузера живы, а у
  новой сессии подписки нет (выход, срок, «Завершить», аварийный выход) — `push-sync.js` показывает плашку
  `#push-restore` (`.update-bar`): «Включить» — `POST` той же `sub.toJSON()`, «Не нужно» — флаг прочь. Сама страница
  push не включает.
- Ссылка «Поделиться», отключённая после `chat_shares.FAILS_MAX` неверных PIN, — push и ntfy владельцу без содержимого.

## ntfy

Прямые уведомления ntfy — `app/ntfy.py`, схема 30: `ntfy_devices` привязаны к digest сессии,
каскад от `sessions` и учётки. Прежние `ntfy_settings` — только шаблон параметров, без отправки.
Миграция сохраняет сервер/токен, назначает разные темы и выключает ntfy у всех устройств;
новая сессия тоже всегда начинает с выключенным ntfy. Общая тема не назначается новому устройству.
«Настройки → Уведомления → ntfy» (`ntfy-settings.js`): HTTPS-сервер из административного allowlist,
тема, необязательный токен, включение, сохранение/проверка/сброс. `GET/PUT/DELETE /api/me/ntfy`,
`POST /api/me/ntfy/test` — только текущая сессия, CSRF и блокировка по общим правилам; сброс
меняет только её настройки, тест шлёт только её теме. Токен шифром
`security.encrypt`, наружу только `has_token`; отсутствующий токен сохраняется лишь у прежнего
сервера, пустой удаляется. Доставка — JSON POST в корень ntfy через `upstream.request` (DNS pinning,
публичные адреса имени, TLS, без redirect, 10 с), без переписки, с `click` на свой origin.
`push.notify_later` отправляет Web Push и ntfy независимо; события мостов и заданий общие.
`GET /api/jobs.push` учитывает ntfy только текущей сессии, чтобы её локальные уведомления не дублировались.
Доставка — включённым непросроченным сессиям активной учётки, с дедупликацией server/topic и
независимой обработкой отказов устройств. Выход/истечение сессии прекращают её доставку.
Клиенты ntfy получают всё из своей темы: для физического разделения доставки темы должны отличаться.
Ссылка `ntfy://` в настройках открывает подписку на сохранённую тему этого устройства. Сервер и тему последнего
сохранения браузер помнит в localStorage `studio-ntfy:<id учётки>` и подставляет в форму, пока у сессии настройки
нет (`configured=false`); токен не запоминается — после нового входа его вводят заново; «Сбросить» забывает и
запомненное. Явный «Выйти» (`form[action="/logout"]`, обработчик в `push-sync.js`) тоже забывает: тема на общем сервере
почти пароль. Конец срока, «Завершить» и аварийный выход её оставляют; флаг `studio-push:<id>`, как и прочие ключи
устройства (`studio-mobile-nav:<id>`), выход не стирает. Тесты: `tests/test_ntfy.py`,
`tests/test_ui_ntfy.py` (integration, 320/1280).
`ntfy` не импортирует `upstream` при загрузке: цепочка main → bridge → push → ntfy иначе
замыкает connections/upstream до объявления `UpstreamRefused`. На Debian Python 3.13 аннотация
`connections.refused` вычисляется сразу, а локальный Python 3.14 скрывал этот сбой. Проверка
холодного импорта — `test_ntfy_import_does_not_start_the_connections_cycle`; после изменения
цепочки импорта дополнительно проверить `import main` на Python хоста до перезапуска службы.
Проверка холодного импорта запускает отдельный процесс и относится к `integration`.

## Язык уведомлений

Решение владельца 2026-11-19: push и ntfy — на языке интерфейса устройства (`ru`/`en`). Язык интерфейса хранится
только на устройстве ([shell](shell.md#язык-интерфейса)), поэтому язык уведомлений — у подписки сессии, схема 51:
`push_subs.lang`, `ntfy_devices.lang` (`DEFAULT 'ru'`, прежние строки и вставки прежнего кода — русские).

- Страница передаёт `lang` в `POST /api/me/push` (`settings.js`, досылка `push-sync.js`) и `PUT /api/me/ntfy`
  (`ntfy-settings.js`). Без `lang` (служебный работник при `pushsubscriptionchange`, вкладка прежней выкладки)
  сохраняется прежний язык сессии — `ntfy.session_lang`, иначе русский.
- Смена языка перезагружает страницу; при запуске `push-sync.js` сравнивает `/api/me.notify_langs` (языки push и ntfy
  этой сессии, `ntfy.session_langs`) с языком устройства и при расхождении шлёт `PATCH /api/me` `notify_lang` —
  `ntfy.set_session_lang` меняет обе строки только этой сессии. Новых маршрутов нет.
- Тексты — `{язык: текст}` рядом на сервере: `push.TITLES` (английское имя «Агентов» — из `en.js`), `push.STUDIO`,
  `push.JOB_NOTICES`, `bridge.ASK_WORDS`, `bridge.DONE_WORDS`, уведомления копии базы (`admin.CHECK_NOTICE`…),
  отзыв ссылки «Поделиться», проверка ntfy (`ntfy.TEST_NOTICE`). `ntfy.pick` выбирает текст по `lang` каждой подписки
  (строка — одна на все языки). Имена компьютера и проекта не переводятся; содержимого в уведомлениях по-прежнему нет.
  Совпадение английских слов с `en.js` сверяет `tests/test_sections_meta.py`.
- Дедупликация ntfy по server/topic (`ntfy.notify`) оставляет последнее устройство выборки: у общей темы двух устройств
  с разными языками уведомление придёт на языке одного из них.

## Ловушки

- Ключ VAPID — в базе (`settings` `vapid`) шифром `STUDIO_DATA_KEY`, не в vault: сменили ключ данных — служба
  заводит новый ключ VAPID и стирает все `push_subs` (браузеры подписаны на прежний открытый ключ), push на
  устройствах включают заново.
