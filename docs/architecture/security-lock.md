# Вход, сессии, блокировка, журнал безопасности

## Вход и сессии

- `auth` — вход по логину или email и паролю, сессии на сервере (cookie `__Host-studio_sid`, 30 дней), CSRF (заголовок
  `x-studio-csrf` у изменяющих запросов), пауза после неудач, признак «заперто»; всё `/api/*` — через `auth.guard`
  (HTTP-middleware; анонимные входы — CLAUDE.md «Инварианты»).
- `guard` видит только заголовки, а тело идёт потоком (nginx — `proxy_request_buffering off`): пока клиент его тянет,
  учётку могут отключить, разжаловать, запереть или закрыть сессии. Поэтому `auth.recheck` повторяет сессию
  (`_live(…, renew=False)`) и блокировку после тела и кладёт свежую учётку в `request.state.user` (роль для
  `auth.require_admin` — из базы): зависимость всего приложения (`main.app`, FastAPI читает объявленное тело до
  зависимостей; асинхронная `auth.recheck_after_body` — синхронную FastAPI увёл бы в поток к общей базе) и вызов в конце чтения потоком — `auth.small_body`, `forms.read_body`, `documents` и записи
  расшифровки (файл удаляется). GET, открытые входы и WebSocket не затрагивает. Apache ограничивает время тела
  `RequestReadTimeout body=20-1800,MinRate=500` (mod_reqtimeout). Проверки — `test_auth.py`.
- Пароль учётки — не короче `security.PASSWORD_MIN` (8) знаков: `account_profile.check_password` при смене пароля,
  сбросе администратором, принятии приглашения и восстановлении по почте, `manage.py create-admin` — тем же
  пределом; подписи форм («не короче 8 знаков» в `account.js`, `admin.js`) и руководство называют то же число.
- Защита входа от перебора — паузы (на пару «логин + адрес» и на адрес); растущая задержка ответа на неверный пароль
  параллельные попытки не тормозит — на неё не полагаться. Из LAN запрос на публичный адрес приходит с роутера
  (`config.hairpin_ip`): для него пауза — только на пару «логин + адрес», иначе запирался бы весь дом.
- Сессия: `auth.create_session(user_id, device=None)` пишет `sessions.created`, `sessions.device` (`'phone'` |
  `'computer'` по `auth.device_class(ua)`; строка UA не хранится) и `sessions.active` (шаг схемы 34). `screenlock._seen`
  обновляет `active`. `auth.STALE_SEC` = `lock_policy.DEFAULT_TIMEOUT` + `lock_policy.HEARTBEAT_GRACE`.
- Шаг схемы 37 (`db.DEVICES_37`): `session_devices.remember` при входе и `POST /api/lock/alive` сохраняет
  краткие сведения браузера, ОС, доступную модель и последний IP из `auth.client_ip`; исходный User-Agent
  не хранится. Неизвестные сведения — NULL, старые сессии дополняются при следующей отметке своего устройства.
  Имя владельца — отдельный столбец `label`, автоматическое обновление его не меняет. Эти сведения не дают
  прав доступа: браузер может скрыть/подменить их (Windows 10/11 не различаются, сокращённый Android UA
  не раскрывает модель и точную версию ОС). Сетевые запросы для определения модели или геолокации не делаются.
- Возврат после входа: `/` без сессии уводит на `/login`, браузер сохраняет фрагмент (`#/code/…` из push).
  `app/static/login.js` кладёт его в скрытое поле `next` и в `action` формы (неудачная попытка не теряет адрес),
  `api.js::toLogin` (сессия кончилась в открытой студии) переходит на `/login` с текущим фрагментом. Сервер берёт
  `next` только по `auth.NEXT_RE` — экраны `auth.PAGE_SECTIONS` (= `LOADERS` роутера, сверяет `test_sections_meta.py`),
  ASCII-буквы, цифры и `_ - = & .`, до `auth.NEXT_MAX` (512) знаков — и отвечает 303 на `/#/…`; иное — `/`
  (`auth.login_target`). Открытого перенаправления нет: путь всегда этого сайта. Passkey и PIN — только отпирание
  открытой страницы, адрес она не меняет. Проверки — `test_auth.py`, `tests/test_ui_shell.py` (Chromium, WebKit).
- `Clear-Site-Data: "cache"` (`auth.CLEAR_CACHE`) — у `/logout`, `DELETE /api/history` и аварийного выхода: HTTP-кэш
  (медиа — `private, max-age=86400`) стирается, кэш оболочки offline и localStorage остаются (проверено Chromium;
  Safari — нет).

## Блокировка (`screenlock`, `lock_policy`)

- Блокировка на всех устройствах (не только на телефоне): схема 24 — `users.screen_lock_sections` (`["*"]` или
  любые из восьми видимых разделов, без dictation), `screen_lock_timeout` (0–86400 с; 0 — при возвращении),
  `computer_pin_timeout`. Таймер активности с допуском `lock_policy.HEARTBEAT_GRACE` (30) с — больше интервала
  отметок 15 с плюс срок ответа 8 с; `alive.active=false` не продлевает доступ, истёкший доступ отметка не открывает.
- Частичная защита закрывает API выбранных разделов, связанные media и повторное использование файлов, общие выгрузки
  и изменение защиты. Раздел файла — `lock_policy.media_sections`: таблицы `lock_policy.MEDIA_SOURCES` (у «Озвучки» —
  и все образцы голоса `voice_samples`), сканы и файлы снимков «Поделиться» (раздел снимка: «Чат» или «Агенты»);
  вместе — все ссылки `media.REFERENCES`, новую таблицу без раздела ловит `tests/test_lock_policy.py`. Скан принадлежит и своему разделу: `lock_policy.scan_sections` (ocr + chat при `origin=chat`,
  translate при ссылке `translations.scan_id`) и `lock_policy.hidden_scans` (подзапрос для лент) — в `media_sections`
  (исходный PDF, PNG страниц), `lock_policy.blocks` для `/api/ocr/<id>*`, ленте `/api/ocr` (`db.page` с
  `extra`/`extra_args`), `search.find`, `jobs`. Изменяющие `/api/me/ntfy*`, `/api/me/push`, `/api/me/exa-key`, а также
  `/api/me/sessions*`, `/api/me/access*`, `/api/me/emergency`, `/api/me/security-events`, `DELETE /api/me/password-reset` закрывает любая
  частичная защита (GET ntfy/push открыты). Так же — все изменяющие `/api/connections*` (создание, правка адреса,
  ключа и разделов, удаление, паспорт, проверка): иначе запертая сессия перенаправила бы подключение защищённого
  раздела на свой сервер; список и модели (GET) открыты, ключ — по защите «Чата». Реестр маршрутов — `tests/test_lock_policy.py::ROUTES`: новый маршрут без
  классификации роняет тест.
- Закрытые разделы запроса — ContextVar `lock_policy.RESTRICTED` (`auth.guard`), и задача, созданная запросом,
  наследует его. Раннеры очередей на пользователя (`ocr._runner`, `translate._runner`, `transcripts._runner`,
  `speeches._runner`) живут дольше запроса и читают свои же файлы: в начале они сбрасывают его в пустое множество,
  иначе скан из «Чата» при закрытых «Сканах» падал бы «файл документа удалён». Ход чата (`StreamTask`) — часть
  своего запроса и защиту запроса сохраняет.
- Страница в открытом разделе забывает данные защищённых: `POST /api/lock/alive` отвечает ещё `expired` (срок истёк,
  даже если показанный раздел открыт), а ожидание отпирания (`waitOpen`, в том числе таймер 0 при уходе) наступает и
  без отметок — `lock.js` шлёт `studio-sections-locked` ({ sections }; при защищённых «Агентах» — и
  `studio-code-clear`) один раз на истечение. «В работе» (`jobs.js`) убирает строки этих разделов и перечитывает
  готовые за час без `since` (сканы чата и перевода прячет только сервер), «Поиск» (`search.js`) стирает выдачу и
  повторяет запрос. Проверка — `test_ui_page_guards.py`.
- Поиск/задачи фильтруются, code SSE проверяет именно code; закрытие потоков при lock/open — только при защите code
  или всего приложения. Изменение включённой защиты — с паролем. Новый путь, который запертая сессия должна делать, —
  только в `auth.SCREEN_LOCK_PATHS`.
- Отпирание паролем и passkey библиотекой `webauthn`, ключи учётки — таблица `passkeys`.
- PIN учётки — спека 2026-10-28-studio-lock-pin, шаг схемы 17: 4–8 цифр ASCII (`PIN_RE`), хеш `users.pin_hash`
  scrypt, `PUT /api/me/pin` — с паролем учётки, `DELETE` — без; `POST /api/lock/pin` — счёт `users.pin_fails` один на
  учётку, попытка занимает место атомарным `UPDATE … RETURNING` до scrypt, верный — только при том же хеше после
  scrypt; после `PIN_FAILS` (10) — 403 `pin_exhausted`, обнуляют только верный PIN и отпирание паролем (не passkey,
  не новый вход и не смена PIN); пауза пароля PIN не касается; `GET /api/lock` — `pin`, `pin_left`.
- Пароль действий из сессии (отпирание, смена пароля, PIN, ключ, защита, почта, коды входа, аварийный выход) —
  `auth.confirm_password(…, digest=…)`: пауза после `auth.LOCK_FAILS` неудач за 15 минут — по ключу
  `("pw", uid, digest сессии)`, а всех сессий учётки вместе — после `auth.PASSWORD_ACCOUNT_FAILS`. Чужая сессия (в том
  числе запертая: `/api/lock/password`) своими ошибками запирает только себя — владелец со своего устройства
  подтверждает аварийный выход и смену пароля. Пустой пароль — 422 `password` до счёта: забытое поле попытку не
  тратит (иначе пять нажатий «Сохранить» запирали бы и отпирание верным паролем); страница с пустым полем запрос
  не шлёт вовсе («Введите пароль учётки»).
- Страница: шторка, экран блокировки, отметки и помощники passkey — `lock.js` (ставит `api.js` `hooks.locked`: 423
  ждёт отпирания и повторяется; цифровая панель PIN — по `pin`/`pin_left` `GET /api/lock`, набранные цифры только в
  памяти модуля; ответ не пришёл — перечитывает возвращение, таймер и «Открыть»). Вкладки одной сессии
  (cookie общая) делят срок бездействия через `BroadcastChannel('studio-lock')`: действие (не чаще раза в секунду)
  сдвигает локальный срок остальных, «открыто» в одной снимает экран в других только после `GET /api/lock`
  «не заперто» — `test_ui_browser.py::test_tabs_of_one_session_share_activity_and_unlocking`.
- Смена учётки в браузере: страница входа открывается только без сессии и шлёт `BroadcastChannel('studio-session')`
  (`login.js`) — вкладки студии (`api.watchSession`) уходят на вход со своим адресом сразу. Вкладка, проспавшая выход и
  чужой вход, получает в `api.loadMe` профиль другого `id`: прежний не подменяется — оболочка скрыта и перезагружена
  (`test_ui_shell.py`).
- Плееры при запирании: пауза, выход из «картинки в картинке» и полноэкранного режима; `play` (медиа-клавиши, панель
  мультимедиа ОС, кнопка окна PiP) до отпирания ловится при погружении и снова ставит паузу — `visibility: hidden`
  оболочки на звук и окно PiP не действует (`test_ui_page_guards.py`).

`lock-start.js` запускает блокировку до модулей оболочки. HTML `/` получает снимок состояния своей сессии
из `screenlock.snapshot`, без отдельного запроса перед PIN; ответ `no-store`, JSON экранирован в атрибуте
и удаляется из DOM после чтения. При возврате известная панель PIN принимает цифры сразу; отправка
ждёт запирания и свежего состояния, которое не стирает введённое. Запросы состояния объединяются.
Старт без снимка использует ту же область `security`, что HTML и 423 при загрузке профиля.
Состояние и запирание ограничены 8 с. Сервер сохраняет проверку области, CSRF и счётчик попыток.
Ранний старт и задержку сети проверяют `tests/test_ui_webkit.py` и `tests/test_ui_browser.py`.
При возврате до истечения локального срока шторка снимается сразу, отметка `/api/lock/alive` идёт в фоне
и при серверном отказе показывает блокировку. Возврат не продлевает срок; истёкший срок и таймер 0
сразу требуют отпирания. Неизменившаяся история «Агентов» сохраняет DOM, раскрытые шаги, выделение
и ранее загруженные сообщения; изменённая история заменяется свежим снимком, а ответ идущего хода остаётся
в конце ленты до снимка live (ход кончился, пока страница была скрыта, — live отвечает idle и история перечитывается).
Проверки возврата — `tests/test_ui_resume.py` и `tests/test_ui_webkit.py`.

## Сессии учётки, аварийный выход, журнал безопасности (`account`, `security_log`)

- `GET /api/me/sessions` — сессии учётки (время входа и активности, тип, `browser`, `os`, `model`, `label`, `ip`;
  признак — `security_log.handle`, sha256 16 hex, не дайджест). `PATCH /api/me/sessions/<признак> {label}` —
  своё имя устройства до 80 символов, без управляющих символов; пустая строка возвращает автоматическое
  название. Можно назвать текущую и другие собственные живые сессии. Защита — обычные guard, CSRF и блокировка;
  чужая или истёкшая сессия — 404. `DELETE /api/me/sessions/<признак>` — завершить (текущая — 409 `current`): строка
  удаляется, push/ntfy уходят каскадом, `bridge.forget(..., close_computers=True)` — доступ теряется сразу.
- `POST /api/me/emergency {password, agents}` — все сессии, все ссылки «Поделиться» (и на чаты своих компьютеров),
  всегда — выдачи проектов своих компьютеров (`project_access.granted`, `project_access.drop`,
  `project_access.wake`), push/ntfy (и шаблон `ntfy_settings`), по выбору — отзыв компьютеров (DELETE agents,
  `bridge.record('revoke')`, `bridge.drop`).
- `GET /api/me/access` — «Доступы и ссылки»: выдачи проектов компьютеров учётки (участник, компьютер, проект; имя
  проекта — фоновой просьбой `projects` к мосту не дольше `account.ACCESS_NAMES_SEC`, иначе null; `missing` — папки
  нет) и её ссылки «Поделиться» (срок, открытия, неверные PIN, без адреса ссылки). Отзыв одной —
  `DELETE /api/me/access/members/<компьютер>/<проект>/<участник>` (`project_access.revoke`, без моста) и
  `DELETE /api/me/access/shares/<id>`; `DELETE /api/me/access` — «Отозвать всё» (`project_access.revoke_all` и все
  ссылки, `share_revoke` с `detail` all). Чужие строки не видны и не отзываются (404 / 204 без изменений).
  Участник сам покидает совместные проекты чужого компьютера — `DELETE /api/me/access/shared/<компьютер>`
  (`project_access.leave`, без моста; «Покинуть» в «Настройки → Агенты → Компьютеры»): его выдачи этого компьютера
  со вкладками и местом — прочь, ему `project_leave`, владельцу — строка `member_remove` истории подключений с
  устройством `claude_code.MEMBER` без адреса; свой компьютер и компьютер без выдач — 404.
- `GET /api/me/security-events?before=` — журнал `security_events` (шаг 34; `kind` без CHECK, каскад от учётки).
  `security_log.record(user_id, kind, *, detail, digest, device, ip)`, виды — `security_log.KINDS`: вход, неверный
  пароль известной учётки (`detail` login|bridge через `auth.check_password(source=)`), выход, при кодах входа —
  `login_code_sent` (пароль верен, письмо ушло) и `login_code_fail` (неверный код; оба с `detail` login|bridge и
  адресом), отпирание и неудача (password|pin|passkey), `pin_exhausted`, `screen_lock_on`, `screen_lock_off`,
  `screen_lock_change` (область или таймер включённой блокировки изменились), смена пароля, `session_end` (`detail` —
  признак завершённой сессии, страница показывает его начало), `emergency`, `pin_set`, `pin_delete`,
  `passkey_add`, `passkey_delete`, `password_reset`, `admin_grant`, `admin_revoke`, `share_create`, `share_revoke`, `share_pin_fail`,
  `share_locked` (посетитель ссылки — без сессии: `ip=auth.client_ip(request)`, без digest),
  `project_member_add`, `project_member_remove` (без подробности: ни логина, ни проекта; ту же пару пишет история
  подключений компьютера — `agent_events` `member_add`/`member_remove`, шаг схемы 39). Адрес — открыто, как
  `agent_events.ip`. Хранение — `security_log.KEEP_SEC` (180 дней), `security_log.KEEP_MAX` (1000) строк на учётку.
- Шумные неудачи `security_log.NOISY` (`login_fail`, `login_code_fail`, `share_pin_fail`) сворачиваются в пределах
  `security_log.COLLAPSE_SEC` (3600) по виду, адресу, подробности и сессии: `count`, `first` (шаг 36), `created` —
  время последней; строка меняется на месте, id прежний (страницы `before=<id>` повтор не теряют); своя квота
  `security_log.NOISY_MAX` (200). `unlock_fail` не сворачивается. API и выгрузка
  (`takeout.SECTIONS` → `security`, `security_events/0001.json`) отдают `count` и `first`.
- «Удалить всю историю» журнал не трогает (след входов: стирание без пароля — чужая сессия заметала бы следы; как
  `agent_events`).
- Сброс пароля администратором: `users.password_reset` + событие `password_reset` в журнал владельца (без адреса
  администратора); `GET /api/me.password_reset` — после входа владелец один раз видит окно с кнопкой «Открыть «Защиту»»;
  закрытие снимает флаг (`DELETE /api/me/password-reset`), аварийный выход — тоже. Администратор флага не видит.
- Права администратора — галочка «Администратор» в окне «Изменить» панели (`admin.js`; у своей строки выключена:
  сервер ответил бы 409 `self`), PATCH `{is_admin}` только при перемене. Перемена — `admin_grant` / `admin_revoke`
  в журнал затронутой учётки (без адреса администратора), в журнал службы — только id; снятие прав и отключение
  отзывают её ожидающие приглашения ([email-accounts](email-accounts.md)).
- Страница — `account-security.js`: `sessionsBlock`, `accessBlock`, `emergencyBlock`, `securityEventsBlock` в
  «Настройки → Защита» после блокировки.

## Ловушки

- Из LAN запрос на публичный адрес приходит с роутера 10.77.1.1 (петля): для него пауза входа —
  только на пару «логин + адрес» (`config.hairpin_ip`), иначе запирался бы весь дом.
- Блокировка (на любом устройстве) — 423 `screen_locked`, пауза после неудач — 429 `locked`: не путать (и
  имена: `screen_lock*` против `auth.LOCK_SEC` / `locked` / `locked_key`). Новый путь, который
  запертая сессия должна делать, — только в `auth.SCREEN_LOCK_PATHS`.
- Варианты passkey (`/api/lock/challenge`, `/api/passkeys/options`) готовятся до нажатия, а
  `navigator.credentials.get/create` зовётся первым в обработчике нажатия: Safari, если перед ним
  ждали сеть, теряет «нажатие», и Face ID на iPhone не появится (в Chrome всё работает) — сторожит
  `test_open_calls_the_passkey_without_waiting_for_the_network`. Вызов на сервере один на сессию и
  живёт 120 с: варианты старше `lock.FRESH_SEC` готовятся заново заранее (таймер, возвращение), а
  пока идёт вызов устройства, новых не готовить — новый заменил бы подписываемый (403).
- Шторка и экран блокировки — `<dialog>` через `showModal()`: иначе открытое окно просмотра
  (`#viewer`, тоже top layer) осталось бы над ними. Escape их не закрывает (cancel отменён,
  `closedby="none"`, закрытое силой окно открывается снова), а до нового `showModal()` оболочку
  прячет `<html class="shrouded">`.

- id ключа в API — хеш credential id, а не он сам: `DELETE /api/passkeys/<id>` пишет журнал Apache.
- `seen` сессии — только по отметке `POST /api/lock/alive`, а не по любому запросу: опросы разделов
  идут на Android и при погасшем экране.
