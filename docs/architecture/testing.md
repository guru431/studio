Договорённость юнитов, vhost и скриптов выкладки сверяет `tests/test_deploy.py`. Набор идёт восемью процессами
(`-n 8 --dist loadgroup` в `pytest.ini`, pytest-xdist): состояние заданий — модульное, процессы
его не делят; `integration` и `manual` — группой `serial` (хук в `tests/conftest.py`), одним
процессом по очереди. Один тест без параллели — `-n0`. Срок теста (`timeout = 30`, на Windows метод `thread`)
по истечении печатает стеки и роняет процесс (`os._exit`): под xdist — «crashed while running <тест>», а
`pytest_xdist_make_scheduler` (`tests/conftest.py`) не даёт loadgroup повторять упавший тест до предела
перезапусков; под `-n0` итога нет — имя теста в стеках. `faulthandler_timeout = 20` заранее печатает стеки
всех потоков напрямую в stderr до завершения процесса на 30 с: захваченный вывод pytest-timeout под xdist
может потеряться. Замена погибшего процесса получает работу только после передачи своей коллекции тестов:
при нескольких падениях события готовности и сбора приходят в разном порядке (`tests/test_test_scheduler.py`).
Тело теста и финализацию фикстуры проверяет `test_suite_timeout.py`. База фикстуры `studio` — копия схемы
`schema_db` (одна на процесс; SCHEMA на новый файл — ~0,2 с на тест), базы тестов — без fsync
(autouse `no_fsync`): на нагруженном ночью диске набор выходил за бюджет 60 с.
Временный корень pytest — `.tmp/.pytest_cache/main` внутри проекта: нумерация, блокировки и очистка старых
прогонов не пересекаются с другими проектами. Подкаталог стандартного кэша исключён из синхронизации;
внешний индексатор не должен следить за временными базами и файлами тестов. Явные `--basetemp` и `PYTEST_DEBUG_TEMPROOT` сохраняются;
этот контракт проверяет `tests/test_tmp_isolation.py`. Каталоги внутри корня по-прежнему создаёт и
чистит pytest с обычной политикой хранения неудачных тестов.
Набор моста также печатает ранние стеки и полные имена тестов, включая зависание закрытия asyncio Runner.
Его временный корень — `.tmp/.pytest_cache/agent` внутри проекта, с той же поддержкой явных `--basetemp` и
`PYTEST_DEBUG_TEMPROOT`; `agent/tests/test_tmp_isolation.py` проверяет и два одновременных прогона.
Оба набора на Windows используют Proactor из `tools/pytest_support.py`: только WinError 995 действующего
внутреннего чтения IOCP запускает чтение снова. В CPython 3.14.2 этот сбой оставлял callback уже завершённого
executor в очереди без пробуждения и подвешивал Runner. Таймауты, отмена задач и остальные ошибки сохраняются.
`tests/test_windows_loop.py` воспроизводит настоящий CancelIoEx и проверяет доставку из потока и закрытие Runner;
после исправления в Python обход удаляется, когда эта регрессия проходит со штатным циклом.
Три замера поиска в `tests/test_search.py` — `integration`: 20 000 строк, последующие страницы чатов и короткий
префикс большого словаря измеряются последовательно, с прежними пределами. Точечно:
`.venv/Scripts/python -m pytest -q -n0 -m integration tests/test_search.py`.
Проверки документации и самого проверяющего делят AST-кэш в группе xdist `docs`.
Поиск голой константы сначала проверяет нормализованный исходник и не разбирает AST модулей,
в которых такого имени нет; нормализация идентификаторов Python сохраняется.
Обход CSRF-защиты всех изменяющих маршрутов разбит по HTTP-методам без исключения маршрутов;
проверки сессии, CSRF и переборы чужих/недопустимых путей агента делают HTTP-запросы через ASGI
на цикле службы (`tests/http_checks.py`) с текущими cookie и заголовками, без перехода между потоками на каждый путь.
Проверка настоящего multipart с картинкой около 20 МиБ и поведенческие Bash-сценарии окружения,
отката, веток отказа и контейнерного entrypoint — `integration`; их проверки сохранены.
Заполнение всей файловой очереди расшифровок со стиранием истории и отмена многостраничного OCR
тоже `integration`: полный цикл записи/очереди под нагрузкой превышал секунду.
Восемь вложенных картинок за два хода и граница длины перевода на сотнях тысяч знаков — также
`integration`; проверки обычных ошибок ввода перевода остаются быстрыми.
Перезапуск внешних процессов и замеры скорости не должны конкурировать с быстрым набором при проверке его бюджета.
Ожидание карточек Codex/OpenCode использует `agent/tests/turn_events.py`: оно завершается при карточке или
завершении хода, без отдельного короткого таймаута на файловые операции в потоке. Общий срок pytest остаётся
ограничением зависания; управляемая задержка записи и завершение без карточки проверяются в
`agent/tests/test_turn_events.py`.
Сценарии отмены записи медиа выполняются через portal работающего TestClient. Фикстура `write_gate` в
`tests/test_media.py` удерживает I/O до явного разрешения: автоматический выход по пятисекундному сроку
позволял сохранению завершиться раньше проверки отмены. При ошибке теста затвор открывается до закрытия
TestClient; отдельная проверка в `tests/test_suite_timeout.py` подтверждает завершение executor и на этом пути.
Публикационный гейт сохраняет полный stdout/stderr упавшего быстрого набора в отдельном локальном временном файле;
сводка показывает путь к нему и последние 25 строк. Журнал нужен для разбора и остаётся до ручного удаления.
Это относится и к командам контракта, и к запуску по pytest-конфигу; ошибка записи журнала не снимает отказ тестов.
Ожидание `bridge.TASKS`/`push.TASKS` в тестовых `settle` после `gather` обязательно отдаёт цикл
через `asyncio.sleep(0)`: Python 3.14 завершает `gather` готовых задач синхронно, а callback
`TASKS.discard` ещё стоит в очереди. Без уступки `while TASKS` зацикливается и pytest-timeout
убивает worker; регрессия с уже готовой задачей и последующей работой — `tests/test_task_settle.py`.
Клиентские скрипты (`tests/clients.py`): `[ps]`-варианты запускаются через `-Command`-обёртку
`clients.PS_WRAP`, которая переключает вывод на UTF-8 и сохраняет коды выхода `-File`: иначе Windows PowerShell
пишет в трубу кодовой страницей унаследованной консоли, а в 866 нет «—» и «→» — тесты зависели бы от того, кто
их запускает. Проверка — те же тесты из Git Bash (866) и под `cmd /c "chcp 65001 >nul && .venv\Scripts\python.exe
-m pytest -q -m integration tests/test_studio_batch_client.py -n0"`. Сценарии, ждущие настоящую паузу `PollSec`, и разбор скриптов
парсером PowerShell — `integration` (секунды). Сквозные сценарии `clients.RUNNERS` — `integration`
в обеих версиях: настоящие CLI-процессы и локальный HTTP-сервер; Python-варианты под нагрузкой
занимали 1,1–1,7 с. Создание локальной копии с ключом через CLI и проверка кодировки справки в трубе
тоже `integration`. Проверки формата файлов, параметров и пустых заглушек ключей остаются быстрыми.
Три проверки настоящего дочернего процесса `web.RUN` (срок, потоки вывода, очистка окружения)
также `integration`; подставной yt-dlp и проверки его аргументов остаются быстрыми.
