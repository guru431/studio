# Wormsoft Harness 0.1.30: что полезно для Студии

Дата анализа: 2026-10-31. Источник: временная копия `Wormsoft_Harness_0.1.30_source/`.
В репозиторий она не входит: пути ниже вида `src/…` — внутри той копии, а не ссылки.

После анализа реализован пакет studio-agent 0.8.0: `@`-подсказки, диффы, ограниченный поиск по содержимому,
очередь с паузой и редактированием, штатное ветвление Claude/Codex, чтение их подзадач и создание Git-worktree
как отдельного проекта. Исходники Harness и его runtime не переносились. Пользовательские сценарии —
[README](../README.md), точный контракт и пределы — [§11 протокола](superpowers/specs/2026-10-28-studio-code-bridge-protocol.md).
Текст ниже фиксирует первоначальный анализ до реализации; оценка его тестов относится к копии Harness.

Главная ценность для Студии — управление работой с кодом: подсказки файлов, наглядные правки,
управляемая очередь, поиск, ветвление переписки и изолированные рабочие каталоги.
Перенос собственного агентного движка Harness для этого не требуется.

Проверены карта возможностей и архитектурные документы, реализации перечисленных ниже сервисов,
связанные API и компоненты интерфейса, а также соответствующие участки текущей Студии.
В копии найден 91 файл тестов; наличие и сценарии тестов изучены, сами тесты не запускались.
`node_modules` отсутствует. Приложение не запускалось, провайдеры и внешние сервисы не вызывались.
Таким образом, наличие функций подтверждено статическим чтением; их работа в живой сборке здесь
не проверялась. Оценки сложности ниже — оценки интеграции в Студию, а не измеренные сроки.

**Разница архитектур определяет способ переноса.**

| | Harness в этой копии | Текущая Студия |
|---|---|---|
| Исполнение агентных задач | Собственные `AgentLoop`, инструменты и OpenAI-compatible клиент | Claude Agent SDK, Codex app-server, OpenCode ACP на компьютере моста |
| История агентов | Нормализованный SQL-транскрипт на хосте Harness | История установленных CLI на компьютере; сервер Studio её ретранслирует |
| Контроль очереди, инструментов и контекста | Принадлежит самому Harness | Зависит от возможностей каждого CLI и нашего моста |
| Интерфейс | Vue, Pinia, Vite; также Electron | PWA, JavaScript без сборки; отдельный Windows-мост |
| Модели | Собственный каталог и подключения по API | В «Агентах» — настройки и доступ установленных помощников; обычный чат имеет свои подключения |

Это видно в `src/backend/agent/AgentLoop.ts`,
`src/backend/models/ModelRuntime.ts`,
`package.json` Harness и нашем
[app/claude_code.py](../app/claude_code.py).
Описание пакета ещё упоминает pi.dev, но текущий код уже содержит собственный runtime.
Vue-компоненты нельзя вставить в наш фронтенд без адаптации.

**Приоритеты переноса.**

| Порядок | Возможность | Что получит пользователь | Сложность для Студии |
|---|---|---|---|
| 1 | `@`-подсказки файлов | Выбрать точный путь в задании, особенно с телефона | Небольшая–средняя |
| 2 | Цветные диффы в шагах агента | Увидеть изменения и `+N / −M` прямо в переписке | Средняя из-за трёх форматов CLI |
| 3 | Поиск по содержимому агентных чатов | Найти старое решение по словам из переписки | Средняя–высокая |
| 4 | Редактируемая очередь | Изменить или убрать ещё не переданное задание | Средняя–высокая |
| 5 | Форк от выбранного сообщения | Попробовать другую постановку задачи, сохранив исходный диалог | Средняя–высокая, отдельно для каждого CLI |
| 6 | Git-worktree для чата | Работать над независимыми задачами в отдельных каталогах | Высокая |
| 7 | Дерево дочерних агентов | Видеть, кто что делает, читать отдельные результаты | Высокая; начать с просмотра |

**1. Подсказки `@файл` и список реально доступных `/команд`.**

У Harness есть FileIndexService (`src/backend/projects/FileIndexService.ts`):
локальный обход, исключения для служебных каталогов, предел 5000 файлов, кэш на 30 секунд,
до 50 результатов с нечётким поиском. Выбор в композере вставляет относительный путь в текст,
а не загружает содержимое файла. Интерфейс —
`src/frontend/components/ComposerAutocomplete.vue`.

Для Студии: индекс строит мост в границах выбранного проекта; браузер получает только подсказки.
Не обходить внешние ссылки, учитывать исключённые и чувствительные файлы, явно обозначать неполный
индекс. Нынешнее дерево файлов уже есть, но поиска путей из поля задания нет.
Можно переиспользовать ограничения обхода нашего [file_stats.py](../agent/studio_agent/file_stats.py),
не превращая подсказки в подсчёт размеров.

`/`-автодополнение стоит добавлять отдельно, по каталогу конкретного CLI. У Harness оно показывает
шаблоны и skills, которые исполняет его runtime. Консольная команда не обязательно исполняется
через SDK/ACP; нельзя обещать `/model` или `/login`, если текст просто уйдёт модели.

**2. Диффы и понятные заголовки шагов.**

У Harness `src/frontend/components/chat/ToolDiffView.vue`
показывает добавленные и удалённые строки, номера и ограниченный по высоте блок;
`src/frontend/utils/toolShortInfo.ts`
выбирает короткую сводку аргументов для каждого инструмента.
В Студии [stepNode](../app/static/js/code-chat.js) сейчас раскрывает JSON ввода и текст результата.

Стоит перенять отображение, добавив единое необязательное представление правки на мосте.
Особенно полезно сохранить `oldText/newText` из OpenCode: текущий
[opencode.py](../agent/studio_agent/opencode.py) превращает ACP-дифф в текст нового содержимого.
У Codex изменения уже попадают в `input.changes`, у Claude доступны аргументы Edit/Write.
Нужны одинаковый live/history-вид и обычный текстовый вариант для неизвестных инструментов.

Парсер `src/frontend/utils/editDiff.ts` рассчитан на
свой формат `+N/-M`, а не на любой Git unified diff. Он также показывает содержимое `write`
целиком как добавленные строки: это не доказательство, что существующий файл был только дополнен.
При адаптации различать точный дифф, создание файла и доступный только новый текст.

**3. Поиск по содержимому агентных чатов.**

ChatSearchService (`src/backend/search/ChatSearchService.ts`)
ищет по названиям и транскриптам, выдаёт до 50 чатов и трёх фрагментов на чат.
В SessionEntryRepository (`src/backend/database/repositories/SessionEntryRepository.ts`)
есть FTS5 trigram-индекс, отдельный путь для коротких запросов и предел сканируемых результатов.
Это реализованная функция, а не только пункт документации.

В Студии общий [поиск по истории](../app/search.py) уже есть, но агентную переписку он не индексирует;
[code-sessions.js](../app/static/js/code-sessions.js) фильтрует названия сессий.
Нужное расширение — поиск на компьютере моста с результатами «чат → фрагмент → открыть».
Можно начать с ограниченного чтения истории, затем измерить необходимость локального индекса.
Постоянный индекс, если понадобится, должен оставаться локальным и учитывать удаление сессий.
Запрос передавать в теле POST: поисковые слова в URL попадут в обычные журналы запросов.
Центральную копию переписки в БД Studio для этого создавать не нужно.

**4. Очередь: исправить, удалить, продолжить после текущей задачи.**

У Harness есть две очереди: вмешательство на безопасной границе выполнения и сообщение после
полного окончания работы. `LiveSession.pauseQueue/resumeQueue` (`src/backend/sessions/LiveSession.ts`)
временно удерживают очередь; `src/backend/sessions/queueChanges.ts`
атомарно применяет пакет правок и сохраняет связь сообщений с картинками.
Пауза очереди не прерывает текущий прогон. Hold живёт в памяти, не переживает рестарт хоста.

У нас уточнения уже есть: Claude/Codex получают их в текущую работу, OpenCode — последовательно.
Добавка — видимый список ожидающих заданий с редактированием и удалением, плюс понятный выбор
«уточнить сейчас» / «после завершения». Начать проще с очереди, которой владеет мост.
Сообщение, уже принятое CLI через `turn/steer` или SDK query, нельзя объявлять отзываемым.
Между окнами нужны идентификаторы сообщений и проверка версии очереди; продолжить использовать
существующее владение ходом. При перезапуске честно сообщать о потерянной очереди.

**5. Ветвление от конкретного сообщения.**

`ChatForkService.fork` (`src/backend/fork/ChatForkService.ts`)
создаёт новый чат с историей строго до выбранного пользовательского сообщения; его текст
попадает в поле ввода для изменения. Есть связь с родителем, список потомков и запрет на
ветвление во время выполнения задачи.

В Студии есть «Продолжить копией» для занятой сессии Codex
([CodexRunner.takeover](../agent/studio_agent/codex.py)). Это копия истории для продолжения,
а не общий интерфейс ветвления с выбранной точки для трёх помощников.
Перенять стоит именно пользовательский сценарий и навигацию по веткам.
Поддержку точки ветвления и переноса вложений сначала проверить в API каждого CLI;
не подменять настоящую историю кратким пересказом и не редактировать вручную внутренние файлы CLI.
Для обычного раздела «Чат» аналогичная функция тоже полезна: сейчас там есть повтор последнего
ответа, но не выбор старой точки для отдельной ветки.

Форк переписки не откатывает изменения на диске. Чтобы две ветки могли независимо менять код,
нужно отдельное рабочее дерево.

**6. Worktree как окружение чата.**

WorktreeChatService (`src/backend/worktree/WorktreeChatService.ts`)
создаёт дочерний чат в отдельном checkout и наследует переписку;
WorktreeService (`src/backend/worktree/WorktreeService.ts`)
управляет Git-worktree, ветками и необязательным переносом незакоммиченных правок.
Это сильная функция для параллельных исправлений или сравнения двух подходов.

Для Студии это отдельная работа: сейчас [projects.py](../agent/studio_agent/projects.py)
разрешает проекты только как подпапки настроенного корня, а список Claude-сессий явно исключает
worktree. Понадобятся проверенные привязки дополнительных каталогов, правильный cwd во всех
операциях, Git-статус и история каждого помощника, настройка зависимостей и доступ к локальным
неотслеживаемым конфигам. Нельзя просто разрешить произвольный путь от браузера.

Переносить полезно создание и выбор окружения, отображение ветки и путь к результату.
В этом исходнике нет готового полного процесса review → merge → разрешение конфликтов.
Автоматический перенос правок через stash и удаление с force не нужны для первого этапа.
Также не стоит копировать `isDirty()`, который при ошибке `git status` возвращает `false`:
неизвестное состояние должно оставаться неизвестным.

**7. Дочерние агенты как открываемые чаты.**

SubchatService (`src/backend/subagents/SubchatService.ts`)
реально создаёт отдельные дочерние сессии, поддерживает sync/async-запуски, передачу результата
родителю, лимит параллелизма, отмену и восстановление ожидающих результатов при старте.
Для собственных подчатов вложенность ограничена одним уровнем.
Конфигурации ролей читаются из Markdown с frontmatter
(`src/backend/agent/agents.ts`).

Перенять прежде всего дерево «родитель → дочерняя задача», статус, открытие истории и расход.
Сейчас [sessions.normalize](../agent/studio_agent/sessions.py) пропускает сообщения дочерних
Claude-агентов, а [codex.step_of](../agent/studio_agent/codex.py) сводит collab-вызов к обычному шагу.
Сначала проверить доступность дочерних ID, истории и статусов в установленных CLI.
Полноценный собственный координатор, распределяющий задачи между Claude/Codex/OpenCode, —
уже отдельная большая функция. Синтетическую пару tool-call/result из Harness нельзя просто
вставить в закрытую сессию внешнего помощника.

**Другие полезные возможности, после основного списка.**

| Возможность Harness | Что можно перенять | Ограничение для нас |
|---|---|---|
| Панель MCP, каталог tools и skills | Просмотр доступных интеграций, состояния и ошибок подключения | Читать через возможности конкретного CLI; не заводить конкурирующий MCP runtime |
| Группы проектов, ручной порядок, цвета | Организация списка без перемещения реальных папок | Сохранить наши сводки Git/FINDINGS/IDEAS; избранное ранее отложено владельцем |
| Все последние чаты на одной странице | Быстрый возврат в работу по разным проектам | Списки собирать через мост; не сохранять тексты и названия на сервере |
| Обновление приложения с прогрессом | Проверка версии моста и удобное обновление | Harness использует Electron; нам нужен свой механизм и установка только после окончания задач |
| Подготовка PDF/DOCX/DOC перед отправкой | Статус извлечения текста, пометка скана, предпросмотр страниц во вложениях «Агентов» | В обычном чате обработка документов/OCR уже есть; файлы агентов обрабатывать на компьютере моста |
| Карточка HTTP-ошибки и отложенный retry | Понятная причина сбоя и управляемая попытка продолжения | Учитывать retries самого CLI; не повторять уже выполненные действия или ошибки доступа/баланса |
| Горячие клавиши | Переходы между чатами и проектами на desktop | Согласовать с браузером и русской раскладкой |
| `suggest_replies` | Удобные варианты следующего ответа на телефоне | В Harness это системный инструмент с управлением окончанием хода; нужна поддержка CLI, простого UI недостаточно |
| Асинхронные внешние задания | Запуск из автоматизации, ID задания, статус, таймаут, доставка итога | Отдельный авторизованный API; не копировать передачу промпта в GET или обход подтверждений |

Реализации: `src/backend/mcp/tools.ts`,

`src/backend/sessions/LlmRetryService.ts`,

**Что уже есть у нас и не является новым заимствованием.**

Управление несколькими компьютерами и проектами, вкладки и локальные сессии, поток ответа,
вопросы и подтверждения инструментов, выбор модели/усилия/прав, контекст и расход, лимиты
подписок, уточнения во время работы, владение ходом между окнами, сохранение работы при
закрытии PWA, Git-статус, файловый редактор, вложения, голосовой ввод и push-уведомления.
Студия также уже имеет поиск обычной истории, обработку документов и OCR.
Сопоставление сделано с текущими [README](../README.md),
[протоколом и командами моста](../agent/studio_agent/agent.py),
[интерфейсом агентного чата](../app/static/js/code-chat.js) и [документами](../app/documents.py).

**Что в текущую архитектуру не переносить.**

- Собственный цикл агента, провайдеры, compaction и исполнение произвольного `codemode` как часть
  текущего моста. Это новая платформа исполнения с отдельными контрактами, а не улучшение UI.
  У Harness `codemode` использует Node `vm`; сам исходник прямо не считает это границей безопасности.
- Дополнительную внешнюю оценку каждого инструмента через Jev. У Harness есть санитизация полей,
  но это всё равно отдельная отправка данных о действии внешнему сервису и дополнительный запрос.
  Наши подтверждения должны опираться на политику и разрешения соответствующего помощника.
- Копирование истории агентов в центральную БД Studio ради поиска и ветвления.
- Автосохранение черновиков. Harness пишет их в SQL; у нас сохранение черновиков было явно
  отклонено. Текущие черновики агентного поля живут только в памяти страницы.
- Автоматическое удаление переписки из архива: у Harness очистка срабатывает после 90 дней
  в архиве или превышения 30 архивных чатов проекта. Скрытие и удаление истории — разные действия.
- Логирование имён и путей вложений: оно прямо есть в `DocumentProcessingService.processDocument`.
  Также нельзя переносить в логи поисковый запрос из URL. Описание verbose-логов в AGENTS шире,
  чем проверенные HTTP-хуки: последние пишут метаданные запросов и маскируют query-токен,
  поэтому утверждать, что весь payload обязательно журналируется, по этим хукам нельзя.
- Android-обёртку с HTTP-прокси ради микрофона: она решает задачу LAN-доступа Harness;
  Студия уже работает по HTTPS как PWA. Electron-окно также не требуется для переноса функций.
- Внешний control plane и Taskpad-флоу как обязательную часть Студии. В копии есть контракт
  интеграции, но это не исходники полного удалённого сервиса или готовый универсальный планировщик.

Предыдущие решения о черновиках и избранном сверены с архивом идей (`IDEAS-archive.md`, вне Git).
Старую архивную запись об отказе от push нельзя трактовать как текущее отсутствие push:
более поздняя реализация уже описана в README и присутствует в проекте.

**Как внедрять поэтапно.**

Сначала — `@файл` и понятные диффы: они дают пользу без изменения самого исполнения задач.
Затем — локальный поиск и очередь с явной границей «ещё ожидает / уже передано помощнику».
Следующий самостоятельный этап — ветвление и worktree.
Дерево дочерних агентов начать с просмотра того, что реально предоставляет CLI.

Для каждой новой операции моста объявлять возможность в `hello`, сохранять работу старых
мостов и отдельно проверять Claude, Codex и OpenCode. Существенные проверки: live и история,
смена чата и окна, блокировка телефона, reconnect, неподдерживаемый CLI и отсутствие данных.
