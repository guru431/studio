# Скорость интерфейса Studio — аудит 2026-11-03

Проверен код `5dec1f6fe6dd2d3cf1608083db793cf54c8745ec`, без изменения приложения и работающего моста.
Основная причина задержек в «Агентах» — зависимость показа экрана от повторного чтения данных,
которые уже известны, и от завершения посторонних проверок. Отдельная причина зависаний — синхронная
отрисовка больших историй и Markdown.

**Границы проверки**

- Edge headless на Windows, настоящие FastAPI, HTTP и WebSocket из штатного `tests/live_app.py`;
  база, учётка, мост и переписки стенда синтетические. Проверены 1280, 393 и 320 px.
- Два обхода: чат, фото, видео, речь, разговоры, сканы, перевод, поиск, настройки и панель администратора.
  Для «Агентов» отдельно проверены списки, прямой вход в проект, вкладки, возвраты, фоновые опросы,
  длинная история и холодная загрузка модулей. Это проверка интерфейса, без генерации моделей,
  установки обновлений, управления рабочим столом и операций с пользовательскими данными.
- На настоящих локальных проектах измерены каталог папок, сводки Git и журналы, чтение списков
  Claude, Codex и OpenCode. Для CLI запускались отдельные диагностические процессы только чтения;
  работающий Studio Agent не останавливался. Тексты и идентификаторы переписок в отчёт не включались.
- Боевой сайт: `/health`, публичная статика, HTTP-заголовки и состояние службы через SSH только для чтения.
  SHA256 девяти важных файлов интерфейса и API совпал с исследованным деревом после нормализации LF:
  `code.js`, `code-panel.js`, `code-chat.js`, `code-activity.js`, `api.js`, `app.js`, `claude_code.py`,
  `code_activity.py`, `profile.py`.
- В Chrome нет сессии Studio. Рабочий пароль не запрашивался и не подбирался; устаревший пароль из vault
  не использовался. Время авторизованных экранов владельца и настоящий iPhone не измерены.
- Сетевой стенд использует HTTP/1.1 без сжатия; боевой сайт подтвердил HTTP/2 и gzip. Результаты
  эмуляции сети ниже показывают поведение кода, а не точное время боевого сайта.

Числовые результаты: [JSON](2026-11-03-ui-performance.json). Одноразовые измерители сохранены локально
в `%LOCALAPPDATA%/Temp/studio-perf-audit-20261103/`; в рабочие модули они не добавлялись.
Неудавшиеся предварительные запуски измерителя с неверными ожиданиями DOM исключены.
Также исключены две попытки измерить холодный старт через смену hash: это была навигация внутри
документа. Для приведённых ниже замеров выполнены полноценные переходы на новый документ.

**1. Переключение сессий между проектами блокируется чтением списка всех сессий**

Источник: `app/static/js/code.js`, `enter`, `chat`, `chatsOf`, строки 361–378, 552–558.

При смене проекта создаётся новый объект `p` с `listing: null`. Метаданные из `chatLists` восстанавливаются
в `p.info`, но `chat()` всё равно ждёт `chatsOf(p)` в `Promise.all`. Только после ответа списка вызывается
`chatView`, который умеет показать историю из своего кэша. Поэтому кэш истории не помогает пройти
предыдущий сетевой барьер. Внутри того же проекта уже исполненный `p.listing` позволяет показать кэш быстро.

Воспроизведение: два проекта, по две сессии, задержка списка 2200 мс, истории 200 мс, состояния 600 мс.
Задержка списка близка к отдельно измеренному настоящему чтению каталога Codex.

| Переход | Первый текст | Готовность после истории и состояния |
|---|---:|---:|
| Первое открытие чата | 2503 мс | 3135 мс |
| Другая сессия того же проекта, без истории в кэше | 233 мс | 849 мс |
| Уже просмотренная сессия того же проекта | 18 мс | 849 мс |
| Сессия другого проекта | 2451 мс | 3068 мс |
| Возврат в уже просмотренный чат первого проекта | 2464 мс | 3065 мс |

Синтетическое событие возвращения видимости в этом сценарии дополнительного барьера не создало:
кэш показался за 14 мс. Нельзя утверждать, что любой фоновый опрос блокирует переключение.

Предлагается сразу показывать проверенный ранее снимок выбранного чата и сохранённые метаданные
его движка после действующей проверки доступа к разделу и компьютеру. Обновление списка — в фоне.
Отправка, права, фактическая модель, захват чужой сессии и любые изменения должны ждать необходимых
свежих проверок. Для ещё неизвестной сессии нельзя угадывать движок по умолчанию.

**2. Каталоги трёх помощников читаются последовательно**

Источник: `agent/studio_agent/agent.py::_op_chats`, `codex.py::chats`, `opencode.py::chats`.

Мост сначала ждёт Claude, затем Codex, затем OpenCode. До этого весь HTTP-список не готов.
OpenCode дополнительно запускает отдельный ACP-процесс на каждое чтение списка.

| Настоящая операция | Первый замер | Повтор |
|---|---:|---:|
| Claude, проект studio, 31 сессия | 77 мс | 68 мс |
| Claude, appshelf, 25 сессий | 61 мс | 60 мс |
| Claude, llm_routers, 62 сессии | 146 мс | 116 мс |
| Codex, studio, 44 сессии | 2702 мс | 2201 мс |
| OpenCode, studio, пустой список | 519 мс | 546 мс |

Одного распараллеливания недостаточно: оно заменит сумму ожиданий максимумом, но повторный Codex всё
равно занимает секунды. Нужны кэш метаданных на мосте, объединение одинаковых запросов, ограниченный
срок свежести и обновление по событиям. Независимые источники можно читать параллельно с отдельными
бюджетами, сохраняя признак неполноты при отказе одного из них. Постоянное metadata-соединение OpenCode
следует рассматривать после проверки его жизненного цикла, закрытия и восстановления после сбоя.

**3. Готовые сводки проектов ждут окончания всей очереди**

Источник: `app/static/js/code-panel.js::refreshSummaries`, строки 308–348.

Четыре worker читают проекты, складывают результат в Map. `paintSummary` для всех строк вызывается
только после общего `Promise.all`. Названия проектов уже видны, но счётчики, Git и даты остаются «—».

| Стенд: 60 проектов | Названия | Сводки |
|---|---:|---:|
| По 150 мс на каждую сводку | 220 мс | 2941 мс |
| Возврат после другого раздела | 72 мс | 2713 мс |
| Последняя сводка 4 с, остальные по 150 мс | 54 мс | 6438 мс |
| Ширина 320 px, по 150 мс | 36 мс | 2662 мс |

Проверен эксперимент только в тестовом браузере: исходник `code-panel.js` подменялся в памяти ответа,
чтобы сразу рисовать завершённую строку. Файлы приложения не менялись.

| Вариант с одним медленным проектом | Первый готовый счётчик | Все сводки | Запросы сводок |
|---|---:|---:|---:|
| Исходный | 6468 мс | 6478 мс | 60 |
| Отрисовка по готовности | 219 мс | 6436 мс | 60 |

Это примерно 30-кратное сокращение ожидания **первого счётчика в этом эксперименте**. Полный объём
работы не уменьшился. Для сокращения работы нужен следующий пункт; увеличивать количество worker
до десятков без изменения вычислений было бы преждевременно.

**4. Каждое возвращение в «Агенты» пересчитывает все проекты, включая скрытые**

Источник: `code-panel.js::panelView`, `projects`, `refreshSummaries`; `agent/studio_agent/project_summary.py::read`.

Map сводок и время проверки создаются внутри экземпляра панели и теряются при unmount. Новый вход
всегда начинает очередь всех проектов. Прямой вход в один проект на 320 px также запустил 60 сводок,
хотя боковая панель была за экраном (`translateX(-272px)`). Список сессий справа появился за 107 мс,
но ненужные этому экрану проверки продолжились.

Одна сводка читает два журнала, выполняет `git status`, `git log`, проверку GitHub-конфигурации,
перечень remote, shallow и сравнения refs. На шести настоящих репозиториях получено 6–7 Git-команд
и 0,97–2,23 с на сводку. Для GitHub каждый раз выполняется анонимный сетевой запрос с `no-cache`,
тайм-аутом 5 с; общего кэша у этих функций нет. Время зависит от прогрева и нагрузки.

Отдельно вся очередь настоящего каталога с четырьмя worker прошла за **4,70 с**: 40 проектов,
39 Git-репозиториев, шесть с проверкой GitHub. Первая сводка завершилась за 104 мс, первые четыре —
за 522 мс. Это измеритель функций текущего checkout, а не замер HTTP экрана владельца.

Предлагается:

- Снимки сводок держать на мосте, совместно для одинаковых чтений, с раздельной свежестью полей:
  локальные журналы/Git — короткий TTL, GitHub — минуты и явное обновление. Начальные значения TTL
  подбирать замерами; 15–30 с и 2–5 мин соответственно — исходные кандидаты.
- В браузере сохранять метаданные панели между переходами, отдельно по пользователю, компьютеру
  и конфигурации; показывать дату и состояние обновления. Обновлять сначала выбранный/видимые проекты.
- Скрытая мобильная панель не должна запускать новую полную очередь. При открытии панели показывать
  снимок и обновлять видимые строки; сортировка по счётчикам может использовать снимок с пометкой свежести.
- Явное обновление и завершение задания инвалидируют нужный проект. Внешние изменения не считать
  полностью покрытыми событиями Studio: сохранять TTL и возможность ручной сверки.
- GitHub выделить из локальной сводки, чтобы медленный интернет не задерживал локальные счётчики.

**5. Для каждой операции заново обходитcя весь каталог проектов**

Источник: `agent/studio_agent/projects.py::find_project`, `catalog`, `project_id`; `agent.py::_project`.

`find_project` вызывает `catalog`, который заново проверяет все папки. `project_id` внутри обхода ещё
повторяет нормализацию корней. В настоящем корне 40 проектов: один обход 56–73 мс, поиск каждого
из 40 проектов по очереди — 2425 мс только на повторное разрешение пути, до полезной операции.

Нужен короткоживущий каталог `pid → путь`, обновляемый при изменении разрешённых корней/каталога.
Кэш не должен отменять проверку настоящего пути, принадлежности корню и запрет ссылок/reparse points
при доступе к файлам и изменениях: эта проверка защищает границы компьютера.

**6. Лимиты Codex конкурируют с навигацией за один mutex**

Источник: `codex.py::subscription_usage`, строки 219–251, `_metadata`, строки 253–267;
`app/static/js/code-usage.js`, автоматический `load()` при открытии чата.

Проверка account/limits/usage держит тот же `_meta_lock`, что каталог, история и состояние.
Её общий бюджет до 24 с. Управляемая проба с тремя account RPC по 200 мс задержала чтение пустого
списка на 622 мс; без проверки лимитов тот же вызов занял 0,3 мс. Это доказательство конкуренции,
не утверждение о 24-секундной задержке в текущем боевом запуске.

Данные квоты уже имеют 60-секундный кэш. Дополнительно требуется отделить низкоприоритетное чтение
квот от критической навигации или организовать очередь с приоритетом коротких чтений и ограниченными
бюджетами. Сохранить безопасные эфемерные чтения состояния Codex; не заменять их на захват writer
исходного пользовательского thread ради ускорения.

**7. История и поток ответа могут занимать главный поток браузера**

Источник: `code-chat.js::messages`, `stepNode`, `loadHistory`, `paintText`; `markdown.js::renderMarkdown`.

В странице истории до 100 сообщений. DOM всех скрытых шагов создаётся сразу. При смене вкладки
`chatView` снимается и создаётся заново: история в Map сохраняет данные, но не готовые DOM-узлы.
Перед `live` последовательно выполняются история и `loadState`; даже при мгновенном показе кэша
проверка готовности остаётся на этой цепочке.

| Синтетическая история, 393×852 | Готовность | Ответ API | Самая длинная задача браузера |
|---|---:|---:|---:|
| 2 сообщения, 20 шагов | 71 мс | 4 мс | Нет задач ≥50 мс |
| 100 сообщений, 1000 шагов, 1,15 МБ | 184 мс | 38 мс | 91 мс |
| Та же история, замедление CPU ×4 | 971 мс | 18 мс | 565 мс |

CPU ×4 — эмуляция ограниченного процессора, не результат настоящего iPhone.

`paintText` каждые 80 мс заново разбирает весь накопленный ответ: Markdown, DOMPurify, подсветка
всех блоков кода. В стресс-пробе с множеством коротких Python-блоков на CPU ×4 один вызов занимал
123–131 мс для 8,6 тыс. знаков, 1534–1566 мс для 42,7 тыс., 5922–6238 мс для 85,4 тыс.
Это специально тяжёлая структура, а не измерение обычного сообщения владельца.

Предлагается сначала ограничить начальную историю одновременно по сообщениям и байтам, лениво
создавать содержимое закрытых шагов и подгружать старое по прокрутке. Кэш готового представления
нужен с бюджетом памяти и корректным снятием подписок, а не неограниченное хранение всех вкладок.
Для потока — обновлять текущий хвост, откладывать подсветку кода, объединять перерисовки с учётом
их реальной стоимости; финальную разметку строить один раз. Санитизацию сохранять во всех режимах.

Также страницы истории на мосте сначала читают/нормализуют всю переписку и только потом берут хвост:
`sessions.py::history`, `codex.py::history(includeTurns=True)`. Это подтверждено кодом, но стоимость
очень больших настоящих историй отдельно не измерена. Следующий этап — индекс/кэш нормализованной
истории на компьютере с инвалидацией по ревизии и проверкой пагинации на растущем чате.

**8. Несколько независимых опросов повторяют работу**

За 45 с на открытом, но не изменяемом чате стенд зарегистрировал 16 API-запросов: три отметки lock,
по два jobs, общий activity, activity компьютера, Git, список сессий, live и один список компьютеров.
Git и полный каталог сессий принудительно обновляются каждые 20 с; одновременно существуют два
источника активности. Сами таймеры ограничены видимостью/бездействием — их нельзя называть вечными.

Предлагается один общий источник снимков активности, объединение одинаковых чтений и адаптивный
опрос: активные задания быстрее, спокойный экран реже. Изменения получать по имеющемуся каналу
моста и SSE; редкую полную сверку оставить для внешних CLI и потерянных событий. Lock/alive и
контроль принятого задания нельзя удалять вместе с необязательными статусами.

В настройках «Агенты» дважды повторился GET `/api/agents` при каждом открытии: формы умолчаний
и список компьютеров загружают одно и то же независимо. Это небольшой дополнительный расход,
который можно убрать общим обещанием чтения для экрана.

**9. Холодный старт загружает большой граф модулей, тёплый требует сетевых сверок**

При полном открытии `#/code` стенд загрузил 35 JS-ресурсов, 580 958 байт распакованного JavaScript,
и выполнил 69 API-запросов для 60 проектов. Среди загруженного — чат, файлы, Git и прочие средства
рабочего места ещё до их использования. Модули без `?v=` получают `Cache-Control: no-cache`:
браузер использует 304, но при новом документе должен пройти сетевые проверки зависимостей.
Service worker намеренно не кэширует модули. Переход внутри уже открытого документа повторно весь
граф не загружает.

| Полный новый документ, ограничение 4 Мбит/с | Названия проектов | Все сводки |
|---|---:|---:|
| 0 мс дополнительной задержки, холодный HTTP-кэш | 1465 мс | 1727 мс |
| То же, тёплый кэш | 270 мс | 491 мс |
| 80 мс задержки, холодный кэш | 2208 мс | 3844 мс |
| 80 мс задержки, тёплый кэш | 1229 мс | 2841 мс |

Сводки здесь мгновенные на мосте: оставшееся время — модули, сетевые очереди и запросы API.
У стенда HTTP/1.1 без gzip; переносить эти числа напрямую на боевой HTTP/2 с gzip нельзя.
На боевом соединении тёплые чтения нескольких JS/CSS занимали около 9–10 мс. Сжатие уже работает.

После устранения повторных расчётов имеет смысл версионировать весь граф модулей, отложить файлы,
рабочий стол и второстепенные инструменты до открытия, предварительно загружать необходимые модули
выбранного раздела. Возможны лёгкая сборка или корректно версионированные ESM. Простое увеличение
TTL у неизменных имён без версии опасно устаревшим кодом после выкладки. Кэш API и переписок на
диске браузера для этого не нужен.

**Остальные разделы и сервер**

На локальном стенде первый показ оболочки обычных разделов занимал 40–184 мс, повтор — 37–73 мс;
для разделов чат/фото/видео/речь/разговоры/сканы/перевод/поиск — 1–3 API-запроса. Корень настроек —
один, вложенные настройки — 3–4, админка — четыре. Это малые тестовые истории: большие медиа-ленты,
пользовательские загрузки и генерация не покрыты этими числами. Ошибок JavaScript в общем обходе не было.

На боевом сервере в момент проверки `studio-web.service` был active/running, семь задач и около
93 МиБ MemoryCurrent, `/health` отвечал 200. Один снимок не исключает периодическую нагрузку, но
подтверждённые выше задержки воспроизводятся без насыщения этого сервера.

**Порядок ускорения и критерии приёмки**
