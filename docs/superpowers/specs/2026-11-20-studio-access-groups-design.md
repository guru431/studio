# Группы доступа к общим API и MCP — дизайн

Дата: 2026-11-20. Статус: принят владельцем к работе («делай все задачи сразу»).

## Зачем

Администратор уже выдаёт всем учёткам общие API моделей и общие подключения MCP (шаг схемы 55,
`/api/admin/shared`). Владелец хочет управлять этим так же, как в Open WebUI на хосте Spark: общее
выдаётся по группам, а внутри одного MCP разным группам доступны разные инструменты. Например, документы
и речь — всем, картинки и видео — группе «Медиа», служебное — только администраторам.

Первый потребитель — MCP aitools с хоста Spark, подключённый к Studio общим MCP. Его обёртка с HTTP,
авторизацией и файловым контрактом живёт на хосте Spark, вне этого репозитория (раздел «Внешний MCP»).

## Цели

1. Группы учёток: администратор создаёт, переименовывает и удаляет группы и задаёт их участников.
2. Доступ к общему API моделей — «все пользователи» или выбранные группы, на подключение целиком.
3. Доступ к общему MCP — так же, плюс сужение для отдельного инструмента: «только группам …» или «только
   администраторам». Инструмент без своего правила доступен всем, у кого есть доступ к серверу (наследование).
4. Проверка на сервере во всех путях, а не только в интерфейсе: списки моделей и подключений, разделы и их
   умолчания, ход чата, задания разделов, каталог MCP разделов и запуск инструмента, инструменты хода чата и
   их вызов.

## Не цели

- Группы для личных подключений, для разделов целиком, для прав администратора.
- Доступ по отдельным моделям одного общего API: разным группам — разные подключения к тому же API.
- Передача файлов MCP в чате и показ картинок MCP в чате (ограничение Studio остаётся).

## Анти-цели

- Пользователь вне группы видит или запускает закрытую модель или инструмент любым новым запросом (прямой
  запрос API, уже открытый диалог, билет задания, следующий вызов инструмента MCP в идущем ходе).
- Существующие общие подключения после выкладки пропадают у пользователей.
- Откат на прежний код молча открывает закрытое — шаг обхода обязан быть в таблице отката.

## Подходы (выбор)

1. **Наследование** — выбран (решение агента после «делай все задачи сразу»; владелец может пересмотреть).
   У сервера доступ «все» или группы; инструмент без правила — как сервер; правило инструмента сужает.
   Новые инструменты, появившиеся у MCP позже, сразу доступны всем, у кого есть доступ к серверу.
2. Таблица «инструмент × группа», закрыто по умолчанию: безопаснее к новым инструментам, но десятки галочек
   и обход после каждого обновления MCP. Отклонён как тяжёлый в работе.
3. Разбивка на стороне MCP (разные токены — разные наборы инструментов, в Studio — доступ на подключение):
   отклонён владельцем — управлять нужно в панели Studio.

Способ проверки один: фильтр в узких местах, где общие строки (`user_id IS NULL`) попадают к учётке
(`connections.list_for`/`get`, `sections._rows`, `mcp_client.servers`/`row`/`present`, `mcp_client.Tools`,
`mcp_sections.supported`). Проверка в каждом обработчике API пропускала бы пути.

## Правила доступа

- Администратор (`users.is_admin`) видит и вызывает всё общее без групп.
- Общее подключение или MCP без правила — «все пользователи»; так остаются все существующие после выкладки.
- Правило с группами — только их участникам; правило без групп — только администраторам.
- Инструмент MCP: доступ к серверу И (нет правила инструмента ИЛИ участник одной из его групп). Правило
  инструмента с пустым списком — только администраторам.
- Служебные вызовы, которые Studio делает сама, правилами инструментов не проверяются, только доступом к
  серверу: `artifact_upload` при загрузке файла раздела, `job_status`/`job_result` по билету задания, выданному
  этой же учётке. Иначе раздел не загрузит исходник и не заберёт результат разрешённого инструмента.
- Запуск инструмента в разделе проверяет право дважды: до загрузки исходника и непосредственно перед
  `tools/call` (за время загрузки администратор мог снять доступ).
- Уникальность имени группы — по нормализованному ключу `name_key = casefold()` (SQLite NOCASE и `lower()`
  кириллицу не складывают).
- Смена правил действует на следующий запрос: билеты заданий и файлов MCP, выданные до смены, перепроверяют
  доступ к серверу при погашении (`mcp_sections.redeem`); уже идущий ход чата перед каждым вызовом инструмента
  проверяет правило заново (шаг-ошибка «нет доступа», ход продолжается).
- Пропажа доступа к общему подключению выглядит для учётки так же, как его удаление: модель исчезает из
  выбора, у диалога — существующая реакция на недоступное подключение. Новых слов отказа не вводим, где
  подходят прежние.
- Принятое до смены правил доделывается (решение агента): задания разделов в очереди и в работе держат свой
  снимок подключения, `connections.token` доступ не проверяет; идущий ход чата продолжает раунды модели;
  фоновые пути (наблюдатель роликов `videos._connection`, `ocr.resume_queued`, `ocr.lease_lost`, release карты)
  ищут подключение без фильтра доступа. Фильтр — по умолчанию у `connections.get`/`list_for`, внутренние
  фоновые пути отключают его явно; новые запросы учётки идут только через фильтр.

## Данные — шаг схемы 56 (только добавление)

```
access_groups(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL, created REAL NOT NULL)
  уникальность имени без учёта регистра (индекс по lower(name) или COLLATE NOCASE)
access_group_members(group_id → access_groups ON DELETE CASCADE, user_id → users ON DELETE CASCADE,
  PRIMARY KEY (group_id, user_id))
access_rules(id INTEGER PRIMARY KEY AUTOINCREMENT, kind TEXT NOT NULL CHECK (kind IN ('connection','mcp')),
  item_id INTEGER NOT NULL, tool TEXT NOT NULL DEFAULT '', UNIQUE (kind, item_id, tool))
  tool = '' — правило подключения или сервера; tool = имя — правило инструмента (только kind = 'mcp')
access_rule_groups(rule_id → access_rules ON DELETE CASCADE, group_id → access_groups ON DELETE CASCADE,
  PRIMARY KEY (rule_id, group_id))
```

Правила удаляются вместе с подключением или сервером (триггеры `AFTER DELETE` на `connections` и
`mcp_servers`); id этих таблиц не повторяются (`AUTOINCREMENT`), так что чужое правило к новой строке не
прилипнет. Правило с группами, все группы которого удалены, остаётся правилом без групп — «только
администраторам», а не «всем»: удаление группы не открывает закрытое.

**Откат на прежний код (шаг 55):** таблицы он не читает, закрытое становится общим для всех. Снятия моделей
с общих API мало (ревью Codex): повтор старого скана берёт подключение из записи скана. Поэтому перед откатом
блокируются сами ограниченные элементы, обратимо: SQL `access.ROLLBACK_56` сохраняет в `access_rollback`
ключ каждого общего API с правилом и заменяет его неверным (прежний код отвечает «токен не расшифровался»),
а общие MCP с правилами выключает, запомнив прежнее `enabled`; после возврата вперёд `access.FORWARD_56`
всё восстанавливает. `connections.token` с выпуска 0.38.2 не менялся — тест через него равен проверке на
прежнем коде.

## Сервер

- Новый модуль `access.py`: чтение групп учётки и правил, проверки `connection`/`mcp`/`tool`, фильтр SQL для
  узких мест, CRUD групп и правил для панели. Состояние — только в базе, без кэша в памяти процесса
  (правка администратора действует сразу).
- Узкие места: `connections.list_for`, `connections.get` (общая строка без доступа — как отсутствующая),
  `sections._rows` и всё, что от них (`links`, `default`, `resolve`, `all_out`); `mcp_client.servers`, `row`,
  `present`; `mcp_client.Tools.discover` (отбор инструментов) и `Tools.call` (повторная проверка правила
  инструмента); `mcp_sections.catalog` и `run` (отбор в `supported`), служебные `upload_artifact`/`status`
  — без правил инструментов.
- Административные пути с `uid = None` (управление общим) правил не применяют. Пути администратора к чужой
  учётке (`/api/admin/users/{uid}/sections` и т. п.) показывают картину этой учётки — с её доступом.
- API администратора (`/api/admin`, наследует `auth.require_admin`):
  - `GET /groups` — группы с участниками; `POST /groups` {name}; `PATCH /groups/{gid}` {name};
    `DELETE /groups/{gid}`; `PUT /groups/{gid}/members` {user_ids};
  - `GET /shared/connections/{id}/access`, `PUT … {groups: null | [gid]}` (`null` — все пользователи);
  - `GET /shared/mcp/{sid}/access`, `PUT … {groups: null | [gid], tools: {имя: [gid]}}` — `tools` задаёт
    полный набор правил инструментов (отсутствующее имя — правило снято); имя инструмента — по
    `mcp_client.NAME`, неизвестное серверу сейчас допускается (инструмент мог временно пропасть);
  - `GET /users` дополняется группами учётки (для показа в списке).
- Пользователь для общего MCP: каждый запрос Studio к общему серверу (`mcp_client.Session` с владельцем
  `None`: RPC, загрузка и скачивание файлов) несёт заголовок `X-Studio-User` — постоянный непрозрачный
  идентификатор учётки (HMAC id учётки ключом из `STUDIO_DATA_KEY`, hex), не логин и не id. Личным MCP
  заголовок не отправляется; одноимённый заголовок из настроек подключения запрещён (`mcp_client.FORBIDDEN`).
  Так MCP может развести папки, задания и файлы по людям.
- Журнал — события с id и числами, без имён групп и инструментов (инвариант приватности журнала).
- Версия Studio — minor: 0.39.0.

## Интерфейс (панель администратора)

- Блок «Группы»: список с числом участников; «Создать группу»; у группы — «Участники» (диалог со списком
  учёток и галочками), «Переименовать», «Удалить» (подтверждение).
- «Общие API моделей»: у каждого общего подключения — «Доступ» (диалог: «Все пользователи» / «Выбранные
  группы» с галочками; без выбранных групп — «только администраторам»).
- «Общие подключения MCP»: у каждого сервера — «Доступ»: доступ к серверу (как выше) и список инструментов
  (живой список «Проверить»; плюс имена из правил, которых сейчас нет у сервера, — с пометкой). У инструмента —
  «Как у подключения» / «Группам: …» / «Только администраторам».
- Подписи — через `tr` и `en.js`; 320 и 1280 px. Пользователь нового интерфейса не видит: недоступное просто
  не появляется.

## Внешний MCP со своим файловым контрактом (хост Spark, вне репозитория)

Делается в этой же работе (владелец: «делай все задачи сразу, не дели»), подключается только к экземпляру
Studio, который о нём просили; второй экземпляр Studio порта не получает. Исходник обёртки — вне репозитория
Studio (он публикуется), на хосте Spark в своём каталоге рядом с aitools, со своими тестами и запиской для
автора aitools; приёмка — живым MCP через «Проверить» и разделы Studio.

Чтобы инструменты aitools работали в разделах Studio, на хосте Spark рядом с aitools ставится отдельная
обёртка и своя служба; исходник aitools и его запуск для ZeroClaw и Open WebUI не меняются. Обёртка:

- Streamable HTTP с обязательным `Authorization: Bearer`, проверка `Host`; порт открыт только хосту Studio;
- личная папка на каждого пользователя Studio, как личные папки Open WebUI на Spark: папка, задания и файлы
  выбираются по заголовку `X-Studio-User`; без заголовка — отказ; без `run_python` и `youtube_cookies`;
  папки Studio — в своём корне, не в папках Open WebUI и не в папке агента ZeroClaw (там папка aitools по
  умолчанию);
- инструменты aitools вызываются тем же способом, что в Open WebUI, — `aitools_cli.py call` отдельным процессом
  с `AITOOLS_WORKSPACE` пользователя; список и схемы — `aitools_cli.py list`; номер фонового задания aitools —
  из ответа инструмента («фоновое задание …», как разбирает обёртка Open WebUI), его состояние — `job.json`
  задания в папке пользователя. Внутренние функции aitools обёртка не импортирует;
- вызов инструмента, не уложившийся в ~25 с (у Studio срок RPC — `mcp_client.TIMEOUT`), продолжается фоном
  и становится заданием обёртки `job_…`: ответ модели — номер задания, дальше `job_status`/`job_result`;
- контракт MCP-сервисов, который уже понимает `mcp_sections`: `artifact_upload` → `art_<32 hex>`;
  инструмент раздела возвращает `structuredContent.id = job_<32 hex>`; `job_status` → `{status: queued |
  running | completed | failed, error?}`; `job_result` → `{result: {artifacts: [{id, mime_type, name,
  download_path: /artifacts/{id}/content}]}}`; `GET /artifacts/{id}/content` с тем же Bearer и Range;
- разделы (ревью Codex: страница прячет инструмент с обязательным полем, которого нет в форме раздела, —
  `mcp-sections.js`): инструменты aitools не переопределяются, обёртка добавляет свои с полями форм Studio —
  «Фото» — `image_generate(prompt, size, n, seed)` без `model` (модель — выбор администратора на панели Spark),
  «Видео» — `video_create(artifact_id, prompt, seconds, seed)` (aitools `animate_image`), «Сканы» — `ocr_image(artifact_id)`:
  Studio передаёт MCP одну картинку (PNG), документы через разделы не идут — только в чате инструментами aitools
  по пути; остальные инструменты aitools — для чата как есть;
- граница папки учётки — в обёртке, не только `AITOOLS_WORKSPACE`: аргументы-пути (`path`, `paths`, `video`,
  `audio`, `subtitles`, `image`, `files`, `source`, `template` и др., как у обёртки Open WebUI) раскрываются с
  симлинками и должны остаться в папке учётки вне служебных `.studio`, `.jobs`, `.secrets`; иначе отказ без
  запуска aitools; задания и файлы другой учётки — «не найдено»;
- срок хранения файлов и заданий обёртки — сутки;
- адреса и токен — только в настройках хостов и в базе Studio, в репозиторий не попадают.

## Тесты

- Быстрый набор: новый `tests/test_access_groups.py` — видимость общих подключений и моделей в разделах и
  умолчаниях, ход чата с закрытой моделью, список MCP, каталог и запуск инструмента раздела, инструменты хода
  и повторная проверка при вызове, служебные вызовы по билету, администратор видит всё, удаление группы не
  открывает закрытое, удаление подключения уносит правила, миграция с шага 55.
- `tests/test_docs.py` сверяет символы документации; браузерный сценарий панели (`-m integration`) — группы,
  доступ общего API и правила инструментов MCP на 320 и 1280 px.

## Оставлено исполнителю

Раскладка кода `access.py`, форма SQL-фильтра, разметка диалогов, тексты подсказок, порядок блоков панели.
Решения агента, которые владелец может пересмотреть: наследование правил инструментов (новые инструменты
MCP открыты всем, у кого есть сервер); доделывание принятого до смены правил; «Проверить» администратора
шлёт `X-Studio-User` администратора; служебные инструменты (`artifact_upload`, `job_status`, `job_result`)
в каталоге разделов не показываются и правилами не закрывают служебные вызовы Studio.
