# Cleaner для внешних моделей: ключ провайдера у пользователя, ход через шлюз Cleaner

Дата: 2026-11-22. Статус: проект, ждёт одобрения владельца. Затрагивает два репозитория: `studio` (этот) и
`cleaner` (соседний). Адреса и имена — примеры (`cleaner.example.com`, `10.77.1.x`); реальные — в локальных профилях.

## 1. Зачем

Cleaner должен стать общей службой для всех учёток Studio на s06-llm (там уже стоят и Studio s06, и Cleaner). Цель
владельца — защита: конфиденциальные данные не должны уйти в облачные модели. Нынешняя схема для этого не подходит:

- провайдера и его ключ заводит администратор Cleaner у себя;
- каждому пользователю Studio нужна своя учётка Cleaner и личный ключ;
- через Cleaner работает только текст: без MCP-инструментов, «Интернета», знаний и профиля, с окном предпросмотра
  перед каждым сообщением.

Нужно так: пользователь сам подключает внешнюю модель по API (адрес провайдера и свой ключ) и включает у подключения
Cleaner. Тогда разговор с этой моделью безопасен: провайдер получает очищенный текст, пользователь видит ответ
с восстановленными данными. Администратор Studio может включить Cleaner принудительно для всех внешних моделей,
в том числе тех, что пользователи добавили сами.

## 2. Цели, не-цели, анти-цели

**Цели**

1. Ключ провайдера хранится у пользователя в Studio (шифром, как сейчас у подключений). Cleaner его не хранит.
2. Учётки Cleaner пользователям не нужны: Studio ходит в Cleaner одним служебным ключом, его задаёт администратор Studio.
3. Ход через Cleaner работает со всем, что есть у хода через сервер: MCP-инструменты, «Интернет», базы знаний, профиль
   подключения и роль. Cleaner очищает всё исходящее (системную часть, историю, результаты и описания инструментов)
   и восстанавливает текст ответа и аргументы вызовов.
4. Администратор Studio может одним флажком закрыть все пути текста пользователя в облако мимо Cleaner — в том числе
   нарочные обходы пользователем (6.3, «Внутреннее и внешнее»).
5. Нет обходного пути: недоступный Cleaner — отказ хода с объяснением, а не запрос к провайдеру напрямую.
6. Пользователь видит под своим ответом, что получила модель. Чужие диалоги не видит никто — ни в Studio, ни в Cleaner.

**Не-цели**

- «Агенты» (Claude Code, Codex, OpenCode через мост): они ходят к моделям с компьютера пользователя. Для них остаётся
  нынешний шлюз агентов Cleaner с ручной настройкой CLI. Принудительный режим их не касается.
- Облачные роли шлюза srvllm через Cleaner: Cleaner не ходит на частные адреса, а srvllm — частный адрес. В
  принудительном режиме эти роли просто закрыты (6.3); провести их через Cleaner — возможный следующий шаг.
- Звук и картинки: Cleaner очищает только текст. «Фото», «Расшифровка», «Озвучка» и голосовой ввод через Cleaner
  не работают.
- Предпросмотр «Что получит модель» перед отправкой в новом виде (решение 3).
- Перевод между протоколами провайдеров: Studio говорит с моделями только по Chat Completions, поэтому и Cleaner
  принимает от Studio только его.
- Переделка прежнего вида подключения Cleaner: он остаётся как есть (решение 4, раздел 6.4).

**Анти-цели** (провал, даже если всё «работает»)

- Хоть один путь, где текст хода с включённым или принудительным Cleaner уходит в облако неочищенным: обход при
  сбое Cleaner, прямое подключение из браузера, частный адрес с прокси в облако, откат на прежний код без обхода из 6.6.
- Ключ провайдера в журнале, базе Cleaner, тексте ошибки или ответе браузеру.
- Cleaner, которого через адрес провайдера можно направить во внутреннюю сеть (SSRF).
- Восстановленные оригиналы в запросах веб-инструментов: поисковые запросы и адреса страниц уходят сторонним службам.
- Оригиналы диалогов Studio, видимые в интерфейсе Cleaner кому бы то ни было, в том числе администратору Cleaner.

## 3. Решения владельца (2026-11-22)

1. Через Cleaner работают не только текст, но и MCP-инструменты с «Интернетом».
2. Устройство — вариант А: Studio отправляет ход в шлюз агентов Cleaner, Cleaner ходит к провайдеру пользователя
   (раздел 4).
3. Окна предпросмотра перед отправкой в новом виде нет; отправленное видно после хода.
4. Прежний вид подключения Cleaner остаётся рядом с новым.
5. Видимость — вариант А: интерфейс Cleaner показывает по контекстам Studio только даты, числа и удаление, без текста;
   пользователь Studio видит «Что получила модель» под своим ответом.
6. Принудительный режим нужен для защиты: конфиденциальные данные не должны уйти в облачные модели. Правило
   «внутреннее и внешнее» владелец поручил выбрать мне — выбран запрет обхода (6.3).
7. Разметку склонений владелец поручил выбрать мне — выбран режим написаний шлюза (6.2, п. 4).

| | Как | Плюсы | Минусы |

Адрес провайдера и ключ пользователя приходят в запросе. ## 5. Как сейчас

- Cleaner в Studio — отдельный вид подключения: `connections.cleaner = 1`, адрес Cleaner, личный ключ Cleaner. Модели —
  из облачного подключения Cleaner, разрешённые ключу. Ход: `POST /api/chats/{id}/cleaner-preview` → предпросмотр
  `/api/v1/chats/{ctx}/requests` → отправка по квитанции → SSE восстановленного ответа (`app/cleaner_client.py`,
  `docs/cleaner-integration.md`). Перевод — те же квитанции на каждый кусок. Контекст Cleaner — на диалог или перевод
  (`cleaner_contexts`, создаётся `POST /api/v1/chats`); удаление — устойчивая очередь `cleaner_deletions`
  (`DELETE /api/v1/chats/{id}`).
- Шлюз агентов Cleaner (`cleaner/agent_service.py`, спецификация Cleaner 2026-10-28) принимает три протокола.
  У ключа есть вид доступа `upstream`: подключение Cleaner (`provider:<id>`) или подписка. У подписки адрес провайдера
  закреплён в коде, а вход агента (`Authorization`) пересылается провайдеру, не сохраняясь. Чаты шлюза — в режиме
  написаний (раздел 11 спецификации шлюза); журнал отправленного держит зашифрованные копии блоков и удаляет разговор
  после 30 дней без запросов.
- Studio ходит только по списку адресов администратора (`upstream`, имена — только https и публичные адреса,
  соединение с проверенным адресом). К остальным адресам ходит браузер — это прямое подключение, только для чата.
- Cleaner на s06-llm: сетевой экран выпускает наружу только TCP 443 и внутренние сети профиля хоста; сторож процесса
  (`cleaner/egress/watch.py`) пускает только к узлам из настроек.

## 6. Устройство

### 6.1. Ход через Cleaner

```
браузер ──▶ Studio: ход чата (история, инструменты MCP, «Интернет», знания, профиль)
              │  тело Chat Completions, как для подключения через сервер
              │  X-Cleaner-Key: служебный ключ      Authorization: Bearer <ключ провайдера пользователя>
              │  X-Cleaner-Upstream: https://provider.example/v1      X-Cleaner-Chat: <id чата Cleaner>
              │  X-Cleaner-Hold-Tools: <имена веб-инструментов>
              ▼
           Cleaner /agent/openai/v1/chat/completions ── очистка, проверка утечек ──▶ провайдер (443, проверенный адрес)
              ▲                                                                            │
              └──── восстановленный поток: текст, аргументы вызовов; id запроса ◀──────────┘
Studio выполняет вызовы инструментов → результаты уходят следующим запросом тем же путём (очищаются заново)
```

Имена заголовков — предложение, окончательные выбирает исполнитель.

### 6.2. Cleaner

1. **Новый вид доступа ключа — `client`** (адрес провайдера присылает клиент). Такой ключ создаёт только администратор
   Cleaner, как ключ подписки. Он действует только на:
   - маршрутах Chat Completions шлюза: `POST …/chat/completions`, `GET …/models`, самопроверка, просмотр отправленного
     (п. 11);
   - `POST /api/v1/chats` и `DELETE /api/v1/chats/{id}` — создание и удаление контекстов (п. 4).

   Остальные маршруты `/api/v1` (`requests`, `texts` и прочие) ключу `client` закрыты. Ключ — только в `X-Cleaner-Key`:
   `Authorization` принадлежит провайдеру. Ключ Cleaner на месте `Authorization` — 401, как у подписки: иначе он ушёл
   бы провайдеру.
2. **Адрес провайдера в запросе** (`X-Cleaner-Upstream`). Проверки перед каждым запросом:
   - только `https`, без логина и пароля в адресе (`cloud.check_url`);
   - все адреса имени — публичные (`ipaddress.is_global`), IP в адресе — тоже;
   - соединение именно с проверенным адресом (SNI и `Host` — имя), без переадресаций и прокси из окружения.

   Это та же защита, что `upstream._pinned` в Studio: подмена DNS между проверкой и запросом не помогает. Порт может
   быть любым, но сетевой экран на s06-llm выпускает наружу только 443 — на другом порту провайдер будет недоступен.
   Пул соединений — с учётом проверенного адреса, а не только имени.
3. **Ключ провайдера** живёт только в памяти запроса, как вход подписки: не пишется ни в базу, ни в журнал, ни
   в квитанцию; из тела ошибки провайдера и заголовков вычищается (`forward.Upstream` уже делает это для входа
   подписки).
4. **Контекст — чат Cleaner на диалог или перевод.** Studio создаёт его `POST /api/v1/chats` служебным ключом,
   как сейчас создаёт контекст прежнего вида, и передаёт id чата в `X-Cleaner-Chat`. Шлюз проверяет, что чат принадлежит
   владельцу ключа и создан ключом `client`. Ведёт его в режиме написаний (каждое написание и падежная форма — своя
   метка): только так аргументы инструментов восстанавливаются буква в букву, и ядро Cleaner менять не нужно. Внутри
   чата — один разговор шлюза (журнал отправленного). Смены чата раз в 30 дней и при 20 000 сущностей у такого чата
   нет: таблица замен живёт, пока жив диалог. Журнал отправленного удаляется, как в шлюзе, после 30 дней без запросов:
   так в Cleaner не копятся тексты давних диалогов. Повторный ход после этого очищает историю заново (правило 7.2.2
   спецификации шлюза). Удаление контекста — существующий `DELETE /api/v1/chats/{id}`, оно уносит таблицу замен,
   журнал и квитанции. Разделение учёток Studio получается само: контекст — на диалог, а диалог принадлежит одной учётке.
5. **Восстановление текста для браузера.** Ответ показывает страница Studio, поэтому для ключа `client` в тексте
   действует правило FR-7.8: внутри адреса, ведущего на посторонний узел, замены не восстанавливаются. Адрес без
   пробелов шлюз и так держит до конца слова (`DeltaRestorer`), поэтому решение принимается по целому адресу,
   и отдаваемый текст остаётся монотонным. Секреты в тексте остаются метками (FR-7.7), как в шлюзе.
6. **Аргументы вызовов** восстанавливаются точно (раздел 10.3 спецификации шлюза), `hold_secrets` включён. Исключение —
   инструменты из `X-Cleaner-Hold-Tools`: их аргументы отдаются такими, как прислала модель, с заменами.
   Сам список — служебная строка запроса (имена инструментов уже есть в теле); он входит в проверку утечек.
7. **Список моделей** (`GET …/models`) для ключа `client` пересылается на `{X-Cleaner-Upstream}/models` с
   `Authorization` клиента; ответ отдаётся как есть, в нём нет данных пользователя. Самопроверка проверяет ключ, адрес
   (правила пункта 2), слои и доступность провайдера.
8. Слои 4 и 5, удержание картинок и файлов, пределы тела и ответа, 8 одновременных запросов шлюза (`AGENT_WORKERS`)
   работают как сейчас. Сверх предела Studio получает 429 и показывает «Cleaner занят, повторите».
9. Прежние виды доступа и `/api/v1` для прочих ключей не меняются: ими пользуются агенты, другие программы и прежний
   вид подключения Studio.
10. **Сторож выхода в сеть** (`cleaner/egress/watch.py`, SEC-1, NFR-2) сейчас пускает соединения только к узлам из
    настроек. Для запроса с ключом `client` `egress.forward` разрешено соединение с адресом, проверенным по пункту 2,
    на порт 443. DNS-запрос — только для имени из `X-Cleaner-Upstream` этого запроса. Остальным модулям (модели,
    разборщики документов) по-прежнему открыт только список из настроек. Это изменение требования безопасности
    Cleaner — правка ТЗ и спецификации с пометкой «решение владельца 2026-11-22»: оно следует из решения 2 и цели 1,
    пользователь подключает провайдера сам.
11. **Видимость** (решение 5).
    - Интерфейс Cleaner по чатам ключа `client` показывает только даты, число запросов и замен по типам и кнопку
      удаления. Без журнала отправленного, таблицы замен, текста квитанций и экрана проверки. Правило — по ключу,
      создавшему чат, а не по учётке, и действует для любого входа, в том числе администратора. Список таких чатов —
      свёрнутой строкой с числом: их тысячи.
    - Шлюз отдаёт клиенту id каждого запроса (например, заголовком ответа). Маршрут «что ушло модели» по служебному ключу,
      id чата и id запроса возвращает сообщения этого запроса со стороны провайдера: системную часть, историю,
      результаты инструментов с заменами. Плюс число описаний инструментов и замены по типам. Собирается из квитанции
      запроса и журнала отправленного. Запрос, журнал которого уже удалён (п. 4), — понятный отказ «журнал Cleaner
      удалён за давностью».

### 6.3. Studio

**Настройки администратора** («Администрирование → Cleaner»): адрес Cleaner, служебный ключ, проверка связи
и флажок «Cleaner для всех внешних моделей». Адрес Cleaner должен быть в списке разрешённых, его сертификат —
`STUDIO_CLEANER_CA`, как сейчас. Ключ хранится шифром `STUDIO_DATA_KEY` в `settings` и в браузер не отдаётся;
после смены `STUDIO_DATA_KEY` его нужно ввести заново, как настройки SMTP (признак `reenter`). Пока адрес и ключ
не заданы, переключатель у подключений не показывается, а включить флажок нельзя.

**Внутреннее и внешнее.** Внутреннее подключение:

- шлюз s06 (`connections.s06`);
- шлюз srvllm в своих разделах, кроме ролей чата и перевода, которые не `local-*` (`sections.is_local`): они облачные;
- прежний вид Cleaner (`connections.cleaner`): это сам Cleaner, облачный ключ лежит у него;
- подключение вида `openai`, чей адрес есть в списке администратора и узел которого — IP частной сети.

Всё остальное — внешнее: любое имя, публичный IP, `localhost` и частный адрес не из списка, любое прямое подключение.
Почему так: цель — чтобы конфиденциальные данные не ушли в облако. Частный адрес не доказывает, что за ним не стоит
прокси в облако, поэтому внутренним его делает только решение администратора — запись в списке. Панель предупреждает:
«частные адреса из списка считаются внутренними — не добавляйте туда шлюзы в облачные модели».

**Переключатель «Через Cleaner»** у подключения (новый столбец `connections.via_cleaner`). Он есть у внешних подключений
вида `openai` в разделах «Чат» и «Перевод». Подключение с переключателем связывается только с этими двумя разделами,
как прежний Cleaner (`sections.CLEANER`). Правка переключателя не требует повторного ввода ключа провайдера.

**Действующий маршрут** — `via_cleaner или (принудительно и внешнее)`; дальше «подключение через Cleaner». Такое
подключение:

- всегда работает через сервер, даже если адреса провайдера нет в списке разрешённых: сервер Studio ходит только
  в Cleaner, а провайдера проверяет Cleaner (6.2, п. 2). Прямого подключения из браузера у него нет. Частный адрес
  или `localhost` Cleaner отвергнет, и ход откажет словами («Cleaner ходит только на публичные https-адреса;
  локальную модель администратор может добавить в список»);
- в «Чате» отправляет то же тело, что подключение через сервер, со всеми инструментами, «Интернетом», знаниями,
  профилем и ролью, но по адресу Cleaner и с заголовками 6.1. Вложенные картинки Studio не отправляет и отказывает
  словами заранее, как сейчас. Картинки из результатов инструментов удерживает Cleaner;
- в «Переводе» отправляет каждый кусок тем же путём, без инструментов, в одном контексте на перевод;
- «Обновить модели», «Проверить» и «Пробный ответ» тоже идут через Cleaner;
- недоступный или не настроенный Cleaner — отказ хода словами («Cleaner недоступен: данные не отправлены»). Запроса
  к провайдеру мимо Cleaner нет.

**Принудительный режим** (флажок администратора):

- у внешних подключений, личных и общих, переключатель включён и заблокирован;
- облачные роли srvllm в «Чате» и «Переводе» отказывают словами («администратор требует Cleaner; облачные роли srvllm
  через Cleaner пока не работают»);
- внешние подключения в «Фото», «Расшифровке», «Озвучке» и голосовом вводе отказывают словами («администратор требует
  Cleaner для внешних моделей; этот раздел через Cleaner не работает»). Новая связь внешнего подключения с этими
  разделами тоже отказывает;
- выключение флажка возвращает переключатели к сохранённым значениям.

**Веб-инструменты.** Имена встроенных инструментов «Интернета» (`web.KINDS`) и MCP-инструментов с пометкой «интернет»
Studio передаёт в `X-Cleaner-Hold-Tools`. Их аргументы приходят с заменами, и поиск уходит в Exa или на сайт без
настоящих данных. Остальные MCP-инструменты получают оригиналы. «Интернет» в диалогах через Cleaner разрешён (у прежнего
вида он запрещён). Правила защищённого источника MCP не меняются.

**Прочие пути с текстом пользователя.** Правило общее: текст пользователя попадает на внешнее подключение только через
Cleaner. В принудительном режиме и в диалогах через Cleaner других путей нет. Известные пути: ход чата, перевод,
«Пробный ответ», «Знания». Источник векторов и переранжирования «Знаний» задаёт администратор общим подключением
(`knowledge.SOURCE_KEY`). Если этот источник внешний, диалог через Cleaner не использует его и ищет только по BM25.
В принудительном режиме внешний источник не используется вообще: индексация и поиск у всех — только BM25, и панель
об этом говорит. Исполнитель сверяет полноту списка по коду.

**Контексты и удаление** — прежние `cleaner_contexts` и `cleaner_deletions` со снимком адреса Cleaner и ключа.
У нового вида снимок — служебный ключ, у прежнего — личный ключ Cleaner. Создание и удаление у обоих идут одними
маршрутами `/api/v1/chats` (6.2, п. 1 и 4), поэтому очередь, её отсрочки и формат строк общие. Удаление диалога,
перевода или учётки ставит контексты в очередь. Смена адреса или ключа Cleaner администратором ставит в очередь
прежние контексты нового вида с прежним снимком.

**Страница.**
- Диалог показывает признак «через Cleaner», подпись ответа «через Cleaner» остаётся.
- Под ответом хода через Cleaner — «Что получила модель». Окно показывает сообщения последнего запроса хода со стороны
  провайдера, то есть с заменами. Studio хранит у ответа id запроса Cleaner (`messages.cleaner_request`), сам текст не
  хранит, а просит у Cleaner (6.2, п. 11), проверив, что диалог принадлежит учётке. Ссылки «Поделиться» и экспорт
  этого окна не несут.
- Карточка вызова инструмента показывает аргументы, которые получил инструмент (у веб-инструментов — с заменами).
- В меню подключения — переключатель и пояснение, почему он заблокирован.
- Новые подписи — через `tr` (русский и английский). Названия двух видов в интерфейсе различаются: прежний — «Cleaner
  (своя учётка Cleaner)», новый — переключатель «Через Cleaner»; обновить `docs/glossary.md`.

**Журнал.** Только события с id и числами: «подключение N: через Cleaner включено», «ход через Cleaner: код 429».
Без адресов провайдеров, ключей и текста.

### 6.4. Прежний вид подключения Cleaner

Остаётся как есть (решение 4): адрес Cleaner, личный ключ Cleaner, облачное подключение — в Cleaner, предпросмотр
с «Исправить замены», «Ответ модели», «Очищенная копия», «Локальная модель», только текст. В принудительном режиме он
считается внутренним: это сам Cleaner. Переключателя «Через Cleaner» у него нет. Его код и тесты новая работа не
трогает, кроме общих мест: решения «внутреннее или внешнее», очереди удаления и названий в интерфейсе.

### 6.5. Схема базы и версии

- Шаг схемы 63: `connections.via_cleaner INTEGER NOT NULL DEFAULT 0`, `messages.cleaner_request TEXT`. Только
  добавление.
- Studio — minor (0.45.0). Cleaner — запись в его журнале изменений, правка ТЗ (SEC-1, NFR-2, FR-7.8 для ключа `client`)
  и спецификации шлюза; отпечаток кода — как обычно.

### 6.6. Откат

Прежний код не знает `via_cleaner` и принудительного режима. Без обхода он отправит ход такого подключения провайдеру
напрямую (из браузера или с сервера) — это анти-цель. Нужен SQL-обход по образцу `access.ROLLBACK_56`: перед откатом
ключи подключений через Cleaner сохраняются в отдельной таблице и портятся. Прежний код тогда отвечает «токен не
расшифровался», а прямой отправки нет. При возврате вперёд ключи восстанавливаются при старте. Принудительный режим
прежний код не соблюдает: перед откатом администратор решает, отключать ли внешние подключения. `messages.cleaner_request`
прежний код не читает. Очередь удаления совместима: маршрут удаления тот же. Строка 63 в таблице отката `CLAUDE.md`
обязательна.

## 7. Ограничения

- Инварианты `CLAUDE.md`: в журнал — ничего пользовательского; ключи — только `Authorization`; список адресов — сервер
  Studio ходит только к ним. Формулировку инварианта нужно дополнить: данные подключений через Cleaner доходят до
  провайдеров, которых нет в списке, через Cleaner и его проверки; частные адреса списка — внутренние.
- `auth.guard` и CSRF — для новых маршрутов администратора и «Что получила модель»; настройки Cleaner — только
  администратору.
- Шаги схемы — только добавлять; строка в таблице отката.
- Публичный Git (оба репозитория): в отслеживаемых файлах — только примеры адресов, имён и путей.
- Тесты: быстрый набор без сети и реального времени (`clock.NOW`, `httpx.MockTransport`); сквозной — `integration`
  с настоящим Cleaner на петле и заглушкой провайдера (`tests/test_cleaner_contract.py`, `tests/studio_server.py`
  в Cleaner). У Cleaner — свой бюджет 60 с и свои правила (`cleaner/CLAUDE.md`).
- Cleaner на s06-llm: наружу только 443; профиль хоста задаёт сети клиентов, Studio s06 должна в них входить.
- Контракт Studio ↔ Cleaner документируется с обеих сторон: `docs/cleaner-integration.md` (Studio) и
  `docs/studio-api.md` (Cleaner).

## 8. Что оставлено исполнителю

- Точные имена заголовков, маршрута «что ушло модели», полей настроек и способа отдать id запроса.
- Как устроен пул соединений Cleaner с проверенным адресом и как сторож выхода узнаёт проверенный адрес запроса.
- Как чат, созданный `POST /api/v1/chats` ключом `client`, получает режим написаний и признак «создан ключом `client`».
- Как Studio собирает запрос через Cleaner в коде хода (`chat.py`, `translate_text.py`) — без копирования ветки хода.
- Точный SQL обхода отката 63 и порядок «вперёд».
- Тексты ошибок (в духе `upstream.gateway_error`) и подсказок интерфейса.
- Порядок работ: сначала Cleaner (ключ `client`, проверки адреса, сторож, контекст, правила 6.2), потом Studio, потом
  документация и выкладка на s06.

## 9. Дальнейшие шаги (не в этой работе)

  и переводе. Проверить на настоящих диалогах s06 после выкладки.
- Облачные роли srvllm через Cleaner (нужно исключение из запрета частных адресов для заданных администратором шлюзов).

## 10. Приёмка

1. Быстрые тесты обоих репозиториев зелёные; новые тесты:
   - Cleaner: ключ `client` (только `X-Cleaner-Key`, ключ Cleaner в `Authorization` — 401; закрытые маршруты
     `/api/v1`), отказ частного адреса и имени с частным адресом, соединение с проверенным адресом, сторож выхода
     пускает только проверенный адрес запроса, нет ключа провайдера в журнале и ошибках, `X-Cleaner-Hold-Tools`,
     правило ссылок в тексте, пересылка моделей, чат только своего ключа, удаление контекста, интерфейс без текста по
     чатам `client` (и у администратора), «что ушло модели»;
   - Studio: внутреннее и внешнее (все строки правила), решение «через Cleaner», заголовки запроса, отказ без обхода
     при недоступном Cleaner, принудительный режим (разделы, облачные роли srvllm, общие подключения, прямые к частным
     адресам), имена веб-инструментов в заголовке, «Знания» без внешнего источника, «Что получила модель» только своему,
     очередь удаления обоих видов, журнал без данных, обход отката 63.
2. Сквозной `integration`: настоящий Cleaner на петле и заглушка провайдера. Ход с вызовом MCP-инструмента: модель
   видит замены, инструмент получает оригинал, результат инструмента уходит провайдеру очищенным. Поиск «Интернета»
   уходит с заменами. «Что получила модель» показывает запрос с заменами. Удаление диалога удаляет контекст.
3. Живая приёмка на s06 после выкладки: личное подключение с переключателем, общее в принудительном режиме, отказ
   внешнего подключения в «Фото», выключенный Cleaner — отказ хода без запроса к провайдеру, прежний вид Cleaner
   работает как раньше.
