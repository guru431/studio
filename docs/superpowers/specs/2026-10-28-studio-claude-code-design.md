# Студия: раздел «Claude Code» и локальный мост — дизайн

Дата: 2026-10-28. Статус: **одобрен владельцем 2026-10-28.** Проект: `studio`
(репозиторий приватный).

Документ для исполнителя студии и автора Windows-моста. Строится двумя планами по очереди (решение владельца
11): сначала сервер студии (раздел 6) — он проверяется на подставном мосте и фиксирует протокол канала
отдельным документом (§10); затем мост `studio-agent` (раздел 7) по этому протоколу.
Уточнение владельца 2026-10-30: мост — компонент `agent/` общего проекта `studio`, с общей Git-историей.

## 1. Зачем

У Claude Code есть штатная функция Remote Control: сессия работает на машине владельца, а claude.ai/code
и приложение Claude становятся окном в неё. Владелец ею пользоваться не может по одной причине — она
требует входа через аккаунт claude.ai, а у владельца правило «всё через свой сервь» и другие бэкенды
(`claude-switch`). Нужно то же самое, но окном служит студия.

Разобрано в сессии 13.10 (проект `d--vsc-agent` на build-host) и в разговоре 2026-10-28. Владелец работает
только в студии, с любого устройства, где вошёл. Студия управляет локальным Claude Code на Windows-машинах
владельца и передаёт ему весь вывод. Команды, установку программ и работу с файлами делает сам Claude Code
— студия их не выполняет, а показывает и даёт подтвердить.

## 2. Критерий успеха

1. Владелец ставит мост в свой сеанс Windows, вводит логин и пароль студии, имя компьютера, папку проектов
   (например `C:\work\projects`) и, по желанию, PIN. Пароль на машине не остаётся.
2. В профиле студии и в разделе «Claude Code» компьютер виден как «на связи».
3. Владелец открывает компьютер (если задан PIN — вводит его), выбирает проект, нажимает «Новый чат»,
   даёт задание, видит ход: текст ответа по мере написания, шаги (команды, чтение и правки файлов).
4. Claude Code просит подтвердить команду — в ленте карточка с кнопками; телефон лежит с погасшим экраном,
   приходит push «<имя>: ждёт подтверждения»; владелец открывает студию, нажимает «Да» — работа идёт дальше.
5. По окончании хода — push. Владелец закрывает чат; позже открывает его снова и продолжает.
6. В списке чатов проекта видна и сессия, начатая в VS Code или терминале; владелец её загружает целиком
   и продолжает.
7. В профиле — история подключений (привязка, выход на связь, открытие, верный и неверный PIN), которую
   нельзя стереть, в том числе через «Удалить всю историю».
8. Откат `install.sh` на прежний код с новой базой работает.

Критерии 1 и 3–6 целиком проверяются после второго плана (мост); первый план проверяет серверную их часть
на подставном мосте в быстрых тестах.

## 3. Не цели

- Не воспроизводить VS Code: нет дерева с перетаскиванием, нет терминала в студии, нет просмотра diff
  сверх `git status`. Только список файлов, правка текстовых, просмотр `.md` и `.pdf`.
- Студия не хранит текст чатов: только перечень (компьютер, проект, номер сессии, название, состояние,
  время). Полная запись сессии остаётся на машине в файлах Claude Code.
- Не универсальный исполнитель команд: студия ничего не исполняет на машине. Команды, установки и работу
  с файлами делает Claude Code под своими запросами разрешений; студия их передаёт и показывает.
- Мост не служба SYSTEM: работает от того пользователя Windows, который вошёл в Claude Code. Прав у него
  столько же, сколько у этого пользователя.
- Чужого нет: каждая учётка студии видит только своих агентов, свои чаты, свои файлы.
- Поиска по тексту чатов нет (студия текст не хранит).

## 4. Анти-цели — провал, даже если всё «работает»

- Мост, который прячется, притворяется другим процессом, держится на машине скрытно или работает без ведома
  владельца. Он должен быть виден (значок в трее), привязан самим владельцем и отзываться из профиля.
- Угнанные пароль или сессия студии открывают компьютер, у которого задан PIN, без этого PIN. PIN проверяет
  мост на машине, а не сервер. (От взломанного сервера PIN не защищает — §6.3, §8.)
- Ключ устройства читается другим пользователем Windows или лежит на диске открытым текстом.
- Запросы разрешений Claude Code подавляются или авто-одобряются сверх настроек самого Claude Code на машине.
  В студию приходит ровно то, о чём Claude Code спросил бы и в окне VS Code.
- PIN или ключ устройства открытым текстом попали в базу, журнал службы, ответ API (кроме единственной
  выдачи ключа при привязке), выгрузку истории (`takeout`) или браузерное хранилище; пароль студии остался
  на машине моста.
- Промпты, тексты сообщений, содержимое или имена файлов попали в журнал службы, в базу (сверх перечня
  чатов §6.1) или в браузерное хранилище. В ответ API они идут только владельцу учётки, в выгрузку — только
  перечень чатов.
  *Снято в части базы решением владельца (шаги схемы 33 и 36):* снимок агентского чата, который владелец
  сам опубликовал ссылкой «Поделиться», хранится в базе — только шифром `STUDIO_DATA_KEY`
  (`chat_shares.sealed`), до срока ссылки, отзыва, 50 неверных PIN, стирания истории или аварийного выхода,
  и в ночных копиях — пока их не вытеснят 7 более новых. Журнал, браузерное хранилище и выгрузка по-прежнему
  без текстов. Устройство — [docs/architecture/sharing-export.md](../../architecture/sharing-export.md).
- Тексты сессий со всех машин владельца собираются на сервере.
- Мост ходит к хостам или папкам за пределами заданной папки проектов при обзоре файлов (обход через
  junction и символьные ссылки — тоже за пределы).

## 5. Решения владельца (разговоры 13.10 и 2026-10-28)

1. Нужен свой «VS Code с Claude Code» только для компьютеров; с мобильных — продолжать те же сессии через
   свой сервер (13.10). Встроенный Remote Control не подходит: идёт через claude.ai (13.10).
2. Управляет работой Claude Code, который работает на машине (а не модель студии своими инструментами) —
   «studio должна уметь использовать локальный claude code и передавать мне весь его вывод».
3. Любой пользователь ставит мост в свой сеанс Windows; вход в студию — логин и пароль; список агентов — в
   профиле учётки.
4. PIN на каждый подключаемый компьютер — по желанию.
5. История подключений в профиле, без возможности стирания.
6. Отдельный раздел «Claude Code»: в нём подключённые компьютеры, в компьютере — список проектов из папки,
   заданной на мосте.
7. В проекте: «Новый чат»; история прошлых чатов; чаты закрываются вручную, чтобы можно было продолжать;
   одновременно сколько угодно чатов в проекте; список файлов и правка текстовых.
8. В чате: давать задания и следить за ходом; нажимать подтверждения команд и отвечать на вопросы агента;
   просмотр `.md` и `.pdf`; статус git; выбор модели и усилия.
9. Push.
10. Студия хранит только перечень чатов; подгрузить и продолжить можно любую сессию (решение автора по
    согласию владельца «реши сам»).
11. Строить двумя планами: сначала сервер студии, затем мост `studio-agent` (2026-10-28).
    С 2026-10-30 по решению владельца мост находится в `studio/agent/`, в общем приватном репозитории.
12. Компьютер, открытый PIN, остаётся открытым для той сессии студии, пока она не заперлась (экран
    блокировки), из неё не вышли, мост не перезапустился и не прошло 3 часа без запросов (срок изменён
    владельцем 2026-10-30, остальные условия приняты 2026-10-28; §6.3).

## 6. Как устроено — студия (сервер)

Новый раздел `code`. Канал к мосту — исходящее от моста долгоживущее соединение (WebSocket): мост за NAT,
входящих к нему нет. Студия шлёт мосту по этому каналу просьбы (загрузить список, провести ход, передать
ответ на запрос разрешения), мост шлёт обратно поток событий Claude Code. К браузеру студия отдаёт этот
поток своим SSE, как в `chat.py`.

### 6.1 Схема (шаг 19)

Только добавление, прежний код с новой базой работает (раздела `code` он не знает, строки незнакомого
раздела не видит — как при прошлых откатах, `connections._from_row` и `search.KNOWN`).

- `agents` — подключённые компьютеры: `id`, `user_id` (REFERENCES users ON DELETE CASCADE), `name`,
  `key_hash` (хеш ключа устройства, как дайджест сессии), `has_pin INTEGER` (задан ли PIN — для надписи в
  UI; сам PIN на сервере не хранится), `projects_root TEXT` (сообщает мост, только для показа),
  `cc_version TEXT`, `created REAL`, `last_seen REAL`. «На связи» — живое свойство (есть ли канал), в памяти
  модуля, не в базе.
- `agent_events` — история подключений, **append-only**: `id`, `user_id` (ON DELETE CASCADE),
  `agent_id` (без FK — переживает отзыв агента), `agent_name TEXT` (имя компьютера на момент события —
  после отзыва строки `agents` нет), `created REAL`, `kind TEXT` (`enroll`, `revoke`, `online`,
  `offline`, `open`, `pin_ok`, `pin_fail`, `session_start`), `device TEXT` (с какого устройства открыт —
  краткий признак сессии студии), `ip TEXT`. Ни секретов, ни промптов, ни имён файлов.
  «Удалить всю историю» эту таблицу не трогает (код стирания её не перечисляет); уходит только с удалением
  учётки.
- `code_chats` — перечень чатов: `id`, `user_id` (ON DELETE CASCADE), `agent_id` (ON DELETE CASCADE),
  `project TEXT` (id проекта `pid` — хеш имени папки, протокол §5), `session_id TEXT` (номер сессии Claude
  Code на машине), `state TEXT` (`open`/`closed`), `created REAL`, `updated REAL`. Ни текста сообщений, ни
  названия: название даёт машина (`custom_title`, `summary`) — решение плана.
- `push_subs` — подписки push (§6.8), привязанные к сессии студии: `digest` REFERENCES sessions ON DELETE
  CASCADE — выход и конец сессии подписку уносят (решение плана).

«Удалить всю историю» стирает `code_chats` (перечень чатов — это история), но не `agents` (подключённые
компьютеры — настройка, как подключения, пресеты и ключ Exa: убираются только отзывом `DELETE
/api/agents/<id>`) и не `agent_events` (критерий 7). Файлы сессий на машинах студия не трогает в любом
случае — они не её. Поэтому после стирания сессии компьютеров остаются в списках проектов (§6.5) — уже без
отметок студии, открытыми; окно подтверждения «Удалить всю историю» говорит это словами (решение автора).

Выгрузка (`takeout`) несёт `code_chats` и `agent_events` учётки (события — с именем компьютера); `key_hash` в
неё не идёт. Это своя история владельца; текстов чатов в ней нет — их нет на сервере (решение автора).

### 6.2 Привязка моста

- `POST /api/agent/enroll {login, password, name}` → `{agent_id, device_key}`. Проверка логина и пароля —
  тем же путём и с теми же паузами, что обычный вход (`auth.locked`, `auth._login_fails`): учётка студии —
  это право подключать агентов, перебор пароля ограничивается так же. Ключ устройства — длинный случайный,
  хранится в базе только хешем (`key_hash`), в ответе отдаётся один раз. Строка тела — с пределом, как
  `auth.LOGIN_BODY_MAX`.
- Канал: `GET /api/agent/link` с заголовком `Authorization` = ключ устройства, апгрейд до WebSocket. Ключ —
  в заголовке, не в строке запроса (строку пишет журнал Apache). Неверный ключ — 401, отозванный агент
  (строки нет) — 401. Успех пишет `agent_events kind=online` и ставит `last_seen`; обрыв — `offline`.
- Ключ устройства прежней учётке не подходит после смены пароля? Нет: ключ самостоятелен (как сессия), смена
  пароля его не гасит. Отзыв — только `DELETE /api/agents/<id>`.

### 6.3 PIN компьютера (проверяет мост)

PIN задаётся при настройке моста и проверяется мостом, не сервером: угнанные пароль или сессия студии не
открывают компьютер без PIN, а в базе студии его нет ни в каком виде. От взломанного сервера PIN не
защищает и защищать не берётся: страницу студии отдаёт сам сервер, и подменённая страница прочла бы PIN при
наборе — шифрованием в браузере это не обойти (решение автора по итогам проверки; §8).

«Открыть компьютер» в студии → студия передаёт мосту PIN и признак сессии студии (дайджест сессии, не сам
токен) → мост сверяет свой хеш, ведёт счёт неудач локально и после N (например 5) перестаёт принимать PIN,
пока его не разблокируют за самой машиной. Верный PIN открывает компьютер **для этой сессии студии**:
каждая просьба студии к мосту несёт её признак, и мост исполняет только просьбы открытых сессий. Открытость
кончается (уточнение владельца 2026-10-31), когда:

- из сессии вышли или её погасили (выход, смена пароля, `--create-admin`) — сервер перестаёт передавать её просьбы;
- мост перезапустился;
- владелец явно изменил настройки/PIN моста;
- прошло 3 часа без просьб этой сессии (счёт — на мосте; изменено владельцем 2026-10-30).

Блокировка/отпирание экрана студии, обрыв сети и перезапуск сервера сохраняют оставшийся срок PIN
(мост ≥ 0.7.1). Запертая сессия получает 423 и к компьютеру не допускается; её потоки и кэши закрываются.

Другое устройство — другая сессия — свой ввод PIN. PIN закрывает у компьютера всё, кроме строки в списке
компьютеров: список проектов (имена папок) тоже (решение автора). Сервер лишь показывает надпись «PIN:
задан/нет» (`agents.has_pin`, сообщает мост) и пишет в историю `pin_ok`/`pin_fail` по событию от моста.
Компьютер без PIN открывается сразу.

### 6.4 История подключений

`GET /api/agents/events` (или в составе `GET /api/agents`) — записи `agent_events` учётки по убыванию
времени, только чтение. Стереть нельзя: ни отдельного DELETE, ни захвата «Удалить всю историю».

### 6.5 Раздел «Claude Code» (UI)

Вкладка рельса «Claude Code» (`code.js`, `#/code`), после «Перевода». Уровни:

- Компьютеры: `GET /api/code/agents` — агенты учётки с состоянием «на связи/нет», именем, версией Claude
  Code, временем последней связи. Открытие компьютера, если задан PIN, — цифровая панель до списка проектов
  (§6.3; можно переиспользовать панель экрана блокировки из `lock.js`). Пока мостов нет — пустое состояние с
  подсказкой, как подключить компьютер. Компьютер не на связи — только его строка: PIN проверить некому, и
  дальше строки ничего не показывается (решение плана).
- Проекты: `GET /api/code/agents/<id>/projects` — мост отдаёт подпапки заданной папки (каждая подпапка —
  проект). За пределы папки — ничего.
- Проект: «Новый чат»; список чатов (`GET …/chats`): открытые и закрытые, с пометкой, откуда сессия (студия,
  VS Code, терминал); у открытых — «продолжить», у закрытых — «открыть снова».

Перечень — слияние, а не отдельная истина студии: какие сессии есть и их содержимое знает машина
(`list_sessions`); студия поверх хранит только своё — `code_chats` по `session_id` (состояние открыт/закрыт
— понятие студии, в Claude Code его нет; при желании название). Список (`GET …/chats`) этот слой читает, но
строк на найденные сессии не создаёт (записи на GET нет): внешняя сессия видна и без строки `code_chats`
(по умолчанию открыта). Откуда сессия — по метке SDK (`tag_session`): студия метит свои («studio»), без
метки — VS Code или терминал; метка вычисляется при показе, в базе не дублируется.

### 6.6 Чат: ретрансляция потока

- «Новый чат»: студия заводит `session_id` сразу (UUID — SDK принимает заданный `session_id`), создаёт
  строку `code_chats` и ведёт первый ход уже по нему. Отдельного «узнать номер из потока» нет.
- `POST /api/code/chats/<session>/turn {text, model?, effort?}` — ответ SSE, как `/api/chats/`. Студия шлёт
  мосту по каналу просьбу провести ход; мост запускает ход Claude Code (Agent SDK, `ClaudeSDKClient`) и шлёт
  события назад; студия отдаёт их браузеру. События: текст по мере написания, шаг (вызов инструмента с
  аргументами и результатом, правка файла), запрос разрешения, вопрос агента (`AskUserQuestion`), конец хода.
- Подтверждения и вопросы: `canUseTool` на мосте приостанавливает ход и шлёт студии карточку (команда с
  аргументами, или варианты вопроса); студия показывает её браузеру и шлёт push; `POST
  …/chats/<session>/answer {request_id, decision|answer}` → студия передаёт ответ мосту → `canUseTool`
  возвращает. Кнопки как в расширении: «Да», «Да, больше не спрашивать» (мост отражает предложенное правило
  в `localSettings` Claude Code, `updated_permissions`), «Нет, вот что вместо этого». Правила разрешений
  самого Claude Code на машине продолжают действовать — в студию приходит только то, о чём он спросил бы.
- «Остановить»: `POST …/chats/<session>/stop` → `ClaudeSDKClient.interrupt()` на мосте.
- Модель и усилие: список моделей сообщает мост (что умеет Claude Code на этой машине — зависит от
  `claude-switch`). Меняются между ходами: модель — `set_model`, усилие — опцией `effort` при запуске клиента
  (в Python SDK посреди сессии оно не меняется), поэтому сменили усилие — мост поднимает клиента заново с
  `resume` (решение автора). Новый чат берёт прошлый выбор (он на устройстве); существующий начинает с
  «по умолчанию» — `null`, прежние модель и усилие чата (протокол §4): продолжение сессии из VS Code или
  терминала их молча не меняет.
- История чата: `GET /api/code/chats/<session>` — мост отдаёт сообщения (`get_session_messages`), студия
  передаёт браузеру; на сервере не оседает. Любую сессию папки (в том числе из VS Code) мост находит через
  `list_sessions` и продолжает через `resume`.
- Закрытие — ручное (`PATCH …/chats/<session> {state:"closed"}`); закрытый остаётся и открывается снова.
  Сколько угодно чатов в проекте: процесс Claude Code на машине держит только отвечающий сейчас чат,
  остальные поднимаются по `session_id` при обращении.

### 6.7 Файлы и git

- `GET /api/code/agents/<id>/projects/<proj>/files?path=` — мост отдаёт список папки в пределах проекта
  (обход junction и ссылок наружу запрещён — сверять настоящий путь). `GET …/file?path=` — текстовый файл
  до предела (1–2 МиБ); бинарные видны в списке, не открываются. `PUT …/file {path, text, base_version}` —
  сохранить; мост проверяет, не изменился ли файл с момента открытия (его мог поправить Claude), иначе
  предупреждает, а не перезаписывает. Создание, удаление, переименование — не в этой версии.
- `.md` и `.pdf` — просмотр (отрисовка `marked`+`purify` как в студии; PDF постранично). Открываются из
  списка и по ссылке на файл в ленте.
- `GET …/git` — ветка, опережение/отставание от `origin`, изменённые и новые файлы; только чтение.

### 6.8 Push

Настоящие уведомления через service worker (Web Push, VAPID) — самостоятельная добавка, пригодится и
разделам «В работе», переводу, расшифровке. В этом плане push — только для раздела «Claude Code»;
подключение к остальным первоначально было отдельной идеей (решение автора).

Дополнение 2026-10-30: общая подписка также уведомляет об успехе и ошибках картинок, роликов, расшифровок,
сканов, переводов и озвучек. Отмена — без уведомления; текст только о результате, без содержимого и имён файлов,
ссылка ведёт к записи раздела, tag — id записи. Отправка после первого сохранения итога, повторное сохранение
уведомление не дублирует. `GET /api/jobs` сообщает `push` текущей сессии: при подписке локальные уведомления
`jobs.js` уступают серверу, без неё остаются запасным вариантом. Переключатель устройства общий с «Кодом».

- Таблица `push_subs` (подписка на устройство: `endpoint`, `user_id`, `digest` сессии, `p256dh`, `auth`,
  `created`), `GET/POST/DELETE /api/me/push`. Шифрование полезной нагрузки (RFC 8291, aes128gcm) и подпись
  VAPID (ES256) — на уже имеющейся `cryptography`, без новой зависимости (проект держит зависимости скупо).
  Ключ VAPID заводит сама служба при первом обращении и хранит в базе (`settings`, ключ `vapid`) шифром
  `STUDIO_DATA_KEY`, как токены подключений; публичный отдаётся странице. Новый `STUDIO_DATA_KEY` — новый
  ключ VAPID, прежние подписки стираются, push включают заново. Ни vault, ни `studio.env`, ни шага выкладки
  (решение плана: проще прежнего «ключ в vault и `config.REQUIRED`», а потерять базу — потерять и подписки).
- Адрес подписки присылает браузер, а запрос на него шлёт сервер — это новое исключение из правила списка
  разрешённых адресов (CLAUDE.md, «Правила»). Принимаются только https-адреса известных служб push, зашитые
  в код, как адреса `web.py`: `fcm.googleapis.com`, `*.push.apple.com`, `updates.push.services.mozilla.com`,
  `*.notify.windows.com`; иной адрес — 422 при подписке. Исключение вписывается в CLAUDE.md рядом с Exa и
  YouTube (решение автора).
- `sw.js` — обработчик `push` (показать уведомление) рядом с имеющимся `notificationclick`.
- Поводы: запрос разрешения, вопрос агента, конец хода. Текст минимальный («<имя>: ждёт подтверждения»),
  подробности — после открытия студии. Включается отдельно на каждом устройстве (флаг как `studio-notify`).
- iPhone: только в студии, добавленной на экран «Домой» (iOS 16.4+). Уведомления идут через серверы Apple и
  Google — содержимое зашифровано, но факт и время им видны; обойти нельзя даже при «всё через свой сервер»
  — сказать это подсказкой при включении.

### 6.9 Apache

- Канал моста (`/api/agent/link`) — апгрейд WebSocket и долгий таймаут: отдельное правило `ProxyPass`
  (`ws://` или `RewriteRule … [P]` на `Upgrade`), как для `yep.example.com`. Проверить в `test_deploy.py`.
- Поток хода (`/api/code/chats/…`) — тот же режим, что `/api/chats/` (`timeout=600`, `flushpackets=on`,
  `no-gzip`): раньше общего `ProxyPass /`.
- `LimitRequestBody` при правке файла — в пределах правки текстового (1–2 МиБ), общий предел не трогаем.

### 6.10 Переподключение и переживание перезапуска

Источник правды о ходе — машина: ход идёт в процессе Claude Code на мосте, а приостановленный запрос
разрешения — это заблокированный колбэк `canUseTool` там же. Студия и браузер — окна, которые
переподключаются и дочитывают; своего состояния хода студия не хранит.

- Телефон ушёл и вернулся (или SSE оборвался на пределе 600 с): браузер переоткрывает поток
  (`GET …/chats/<session>/live`, SSE), студия просит мост повторить текущее состояние хода — уже написанный
  текст и открытую карточку запроса, если она есть, — и дальше транслирует. Жизнь хода к SSE не привязана:
  он идёт на мосте, пока мост жив.
- Студия перезапустилась (выкладка): реестр каналов и «на связи» — в памяти, но мосты сами
  переподключаются (§7) и заново объявляют идущие ходы и открытые запросы. `POST …/answer` несёт `agent_id`,
  `session`, `request_id`, поэтому студия маршрутизирует ответ мосту, даже если о запросе ничего не помнит;
  колбэк на мосте всё это время заблокирован и ждёт.
- Мост перезапустился (перезагрузка машины, сбой): идущий ход теряется вместе с процессом SDK — как
  `chat.recover()` помечает прерванное. Сессия на диске цела, её можно продолжить; теряется только
  незаконченный ход. Студия показывает ход прерванным.
- Канал моста (WebSocket) держится пингами; таймаут его правила Apache — щедрый, чтобы простой между
  ходами его не рвал.

### 6.11 Приватность и журнал

Правило студии в силе: `--no-access-log`, в журнал — только события с id. Промпты, тексты, содержимое и
имена файлов, PIN, ключ устройства в журнал не идут (сторожат тесты журнала раздела). Анонимны по-прежнему
только `/health`, `/login`, `/logout`, `/robots.txt` и оболочка PWA; `/api/agent/enroll` — анонимен (это и
есть вход мостом, со своими паузами), `/api/agent/link` — по ключу устройства; всё `/api/code/*` — через
`auth.guard`.

## 7. Мост (Windows) — контур

Второй план, компонент `agent/` приватного проекта `studio` (решение владельца 11, уточнение 2026-10-30);
здесь — рамка. Строится по протоколу канала, который зафиксировал первый план (§10).
Опирается на уже существующий в репозитории
`claude-agent-server`/`worker.py` (`llm_routers`): там есть запуск `claude.exe` из каталога расширения VS
Code, вычищенное до аллоулиста окружение дочернего процесса и bearer-аутентификация. Это не проектирование
механизма с нуля, а новый канал у знакомого кода.

- Основа — Claude Agent SDK (`claude-agent-sdk`, pip) поверх установленного `claude` CLI (путь — как ищет
  `worker.py`: новейший `claude.exe` из каталога расширения). SDK даёт событийный поток хода, `canUseTool`,
  `list_sessions`/`get_session_messages`/`resume`/`interrupt`/`set_model`, уровень усилия.
- Работает от вошедшего пользователя Windows: OAuth-сессию Claude в другой профиль не перенести (зафиксировано
  в README воркера). Автозапуск при входе в Windows, значок в трее с состоянием «на связи/нет» — мост виден,
  не прячется.
- Настройка (окно моста): логин и пароль студии, имя компьютера, папка проектов, PIN по желанию. `enroll` →
  ключ устройства; ключ хранится зашифрованным DPAPI (`CryptProtectData`, область пользователя) — прочитать
  может только этот пользователь Windows; пароль студии на машине не остаётся.
- Канал: WebSocket к студии с авто-переподключением. Принимает просьбы студии, отвечает потоком событий.
- Ход: `ClaudeSDKClient` в папке проекта; события SDK → студии; `canUseTool` приостанавливает ход и шлёт
  студии карточку запроса, ответ студии возвращает из колбэка (нужен холостой хук `PreToolUse`, держащий
  поток для `canUseTool` — из документации SDK).
- PIN: хеш на машине (scrypt), счёт неудач и блок после N — на машине; открытые сессии студии и их срок —
  в памяти моста (§6.3); серверу мост сообщает лишь факты (`pin_ok`/`pin_fail`, «задан ли PIN») для истории
  и надписи.
- Пределы: одновременных ходов немного (как `CLAUDE_WORKER_MAX_CONCURRENCY`), чтобы не жечь квоту подписки
  разом.

## 8. Ограничения

- Учётка студии становится правом вести работу через Claude Code на машинах владельца. Защита — PIN
  (проверяет мост), пауза входа (сервер), отзыв агента (профиль), неудаляемая история. Слабое звено —
  разблокированный телефон с открытой студией при машине без PIN.
- Взломанный сервер студии открывает компьютеры: подменённая страница прочтёт PIN при наборе. PIN — защита
  от угнанных пароля или сессии студии, не от сервера.
- Расходуется квота той подписки Claude, что вошла на машине. Машина должна быть включена, мост запущен.
- Политика Agent SDK запрещает сторонним продуктам предлагать вход через claude.ai; про личный сервис на
  своей подписке не сказано — решение владельца (в том же положении Telegram-бот). Мост входом claude.ai не
  распоряжается: Claude Code на машине уже авторизован своим профилем.
- Живость меньше, чем у Remote Control: если ту же сессию открыли и в окне VS Code, писать будут двое —
  студия это предупреждает, но единого «живого» владения не обещает.
- PIN 4–8 цифр при малом числе попыток слабее пароля; кто подсмотрел набор, откроет компьютер.

## 9. Решения автора (не владельца — проверить при чтении)

1. Номер шага схемы — 19 (текущий `db.VERSION` = 18).
2. Канал — WebSocket, не long-poll: долгоживущий двунаправленный.
3. PIN проверяет мост, не сервер: угнанные пароль или сессия студии не открывают компьютер. Счёт и блок — на
   машине. От взломанного сервера защиты нет (он отдаёт страницу) — так и записано, без обещания (§6.3, §8).
4. Студия не хранит текст чатов (приватность; запись и так на машине). Следствие: при выключенной машине
   ничего, кроме строки компьютера, не видно — ни чатов, ни проектов (PIN проверить некому; §6.5).
5. Ключ устройства самостоятелен — смена пароля студии его не гасит (как сессия), гасит только отзыв. Иначе
   мост отваливался бы при каждой смене пароля.
6. Мост `studio-agent` — часть `studio`, каталог `agent/` общего приватного репозитория
   (уточнение владельца 2026-10-30, §5, решение 11); переиспользует подходы `worker.py` из `llm_routers`.
7. Push вынесен как общая добавка студии (нужен и «В работе», переводу, расшифровке).
8. Ход живёт на мосте; студия и браузер переподключаются и дочитывают, своего состояния хода студия не
   хранит. Переживание перезапуска студии — через повторное объявление мостом (§6.10).
9. `session_id` студия задаёт сама (UUID) при «Новом чате»; `code_chats` — слой поверх машины, не источник
   истины; откуда сессия — по метке SDK; список не пишет строк на GET (§6.5, §6.6).
10. Web Push — на имеющейся `cryptography`, без новой зависимости; ключ VAPID — в базе шифром
    `STUDIO_DATA_KEY` (§6.8).
11. «Удалить всю историю» стирает `code_chats`, но не `agents` (настройка) и не `agent_events` (§6.1); сессии
    машин после стирания остаются в списке, окно подтверждения это говорит.
12. PIN закрывает и список проектов, не только действия (§6.3).
13. Push в этом плане — только раздел «Claude Code»; адреса подписок — зашитый список служб push, новое
    исключение из правила разрешённых адресов в CLAUDE.md (§6.8).
14. Выгрузка несёт `code_chats` и `agent_events` (§6.1).
15. Смена усилия между ходами — перезапуск клиента SDK с `resume` (§6.6).
