# Зеркала проекта: группа равноправных копий — дизайн

Дата: 2026-11-22. Статус: согласовано владельцем 2026-11-22.

## Зачем

Владелец держит один и тот же проект на нескольких своих компьютерах (сейчас — минимум три: workstation-a, workstation-b и
третий, где лежит исходный проект) и **правит его на любом из них**. После работы он хочет разнести изменения
с того компьютера, где работал, в остальные копии. Нынешнее «Зеркало» под это не подходит:

1. Зеркало — связь в одну сторону «проект на A → копия на B», записана только со стороны A
   (`project_mirrors.source/project`). Открыв тот же проект на B, владелец зеркала не видит, отправить
   изменения с B на A не может, а «Найденные копии» на B предлагают папку A как непривязанную.
2. Когда у проекта есть зеркало, форма нового скрыта; добавить второе можно только пунктом «Новое зеркало»
   внутри выпадающего списка — владелец его не находит.
3. На кнопке «Зеркало» не видно, есть ли у проекта зеркала и сколько.
4. Сравнение постоянно падает с «обнаружена открытая база SQLite — закройте её и повторите операцию».
   Причина на workstation-a: в `E:\projects\studio\.tmp\.pytest_cache\…` лежат брошенные тестами `studio.db-wal`/`-shm`
   (20–21.11) и пустые `-journal` профиля браузера. `mirror._entry` моста считает любую такую пару открытой
   базой и отказывает во **всём** сравнении; сообщение не называет файл, а «Постоянные исключения» появляются
   только после успешного сравнения — обойти из окна нельзя.

Успех: на любом компьютере с копией кнопка «Зеркало» показывает число остальных копий; окно перечисляет их;
изменения с текущего компьютера уходят в выбранную копию или во все сразу; правка, сделанная в другой копии и
ещё не дошедшая сюда, не затирается молча; открытые и брошенные базы SQLite не мешают сравнению.

## Цели

- **Группа копий.** Все копии проекта на компьютерах владельца — одна группа. Зеркало, добавленное с любого
  компьютера группы, сразу видно на всех остальных (данные — на сервере Studio, мосты ничего не хранят).
- **Отправка с текущего компьютера.** Из окна «Зеркало» открытого проекта — в одну копию (со сравнением,
  как сейчас) или «Отправить во все копии».
- **Индикатор.** В правом верхнем углу кнопки «Зеркало» — цифра: число остальных копий группы. Нет копий —
  индикатора нет.
- **Добавление всегда на виду.** Кнопка «+ Добавить зеркало» в окне, без скрытого пункта списка.
- **SQLite не валит сравнение.** База с незакрытым журналом показана «Пропущен · открытая база SQLite» с путём;
  остальное сравнивается и синхронизируется.
- **Исключения доступны без успешного сравнения** — они теперь общие для группы и показаны всегда.

## Не цели

- Автоматическая синхронизация без нажатия (по таймеру, «после хода») — отдельная идея в `IDEAS.md`
  («Общий список зеркал и «синхронизировать после хода»»), здесь не делается.
- Слияние правок одного файла из двух копий. Копия, правленная отдельно, по-прежнему решается вручную:
  «Оставить в копии» или замена с подтверждением.
- «Забрать» изменения из другой копии в текущую. Отправка идёт только **с** открытого проекта; чтобы разнести
  правки с workstation-b, открывают проект на workstation-b.
- Зеркала проектов, открытых владельцу другими пользователями, и копия в папке, открытой другим (как сейчас:
  `project_mirrors._private_destination`).
- Добавление второй копии проекта на тот же компьютер (бывает только после переноса старых зеркал).
- Общий список всех зеркал учётки (та же идея в `IDEAS.md`).

## Анти-цели (провал, даже если «работает»)

- Копия, отставшая от другой, молча перезаписывает более новые правки в третьей копии.
- Передача начинается без явного действия владельца.
- Имена, пути, содержимое файлов попадают в журнал сервера или моста (инвариант приватности, `CLAUDE.md`).
- Прежний код после отката не может работать с базой (правило «схема — только добавлять»).

## Подходы

Рассматривались три; владелец выбрал **А**.

- **А. Группа копий (выбрано).** Все копии равноправны, каждая видит все остальные, отправка — с любой в любую
  или во все. Одно действие после работы разносит правки на все компьютеры. Цена: новая модель данных
  (группа, копии, пары), перенос существующих зеркал, доработка моста.
- **Б. Двусторонние пары.** Зеркало связывает два компьютера, отправлять можно в обе стороны. Меньше
  изменений, но при трёх компьютерах каждую пару связывают вручную, B не видит C, отправка после работы —
  цепочка. Отклонено: у владельца три и более компьютера.
- **В. Автоматическая синхронизация (как Dropbox).** Отброшено: без сравнения правки одной копии молча
  затирают другую (анти-цель), а передача через сервер идёт только при открытой сессии Studio.

## Как устроено

### Модель данных

- **Группа** — набор копий одного проекта у одного пользователя; хранит общие **постоянные исключения**
  (шифром `STUDIO_DATA_KEY`, как сейчас в `location`).
- **Копия** — папка на компьютере: компьютер (`agents.id`), `pid` проекта на этом компьютере, адрес папки
  для записи (`root` — id папки проектов, `name_key` — `security.digest` имени в нижнем регистре, `location` —
  шифром `{name, folder}`). Одна папка — одна строка (`UNIQUE` по компьютеру, `root`, `name_key`). Новое
  добавление второй копии на тот же компьютер в группу отклоняется; две копии на одном компьютере возможны
  только после переноса старых зеркал (ниже) — тогда окно показывает обе с папками, лишнюю владелец отвязывает
  сам. Копия ищется по открытому проекту: компьютер + `pid`.
- **Пара** — состояние сверки двух копий группы: для каждой стороны — её манифест на момент последней
  синхронизации между ними (шифром), время синхронизации. Пары создаются по мере сравнения и отправки.

Почему база сравнения — у **пары**, а не у копии: если B отправил правку в C, а потом отставший A отправляет в C,
то для пары A–C файл в C отличается от состояния их последней сверки — он показан «Локальное изменение» и не
затирается без подтверждения. С базой «по копии» C считался бы чистым, и новая правка из B пропала бы молча
(анти-цель).

**Что записывается в пару.** После отправки X → Y:
- состояние Y — как сейчас `project_mirrors._next_baseline` (оставленные в копии файлы сохраняют прежнее
  состояние и при следующей сверке снова показаны);
- состояние X — манифест X из этой отправки **до** приведения к платформе назначения
  (`project_mirrors._portable` меняет словарь на месте — нужна копия), **кроме** путей, которые в Y не
  применены (оставленные в копии, пропущенные, исключённые): для них остаётся прежнее состояние X. Иначе
  обратная отправка Y → X молча заменила бы правку X версией, которую владелец оставил только в Y.

Первая сверка совпадающих копий фиксирует оба состояния, как сейчас фиксируется база (`compare` при
`baseline IS NULL`).

**Когда запись копии — «локальное изменение».** Сверка X → Y (X — открытый проект), путь `p`, запись Y — `y`:
1. `y` совпадает с записью X — изменений нет (как сейчас);
2. `y` равна состоянию Y в паре X–Y — не локальное изменение (как сейчас);
3. `y` (существующий файл, ссылка или папка) равна состоянию **X** в любой из пар X — тоже не локальное: X уже
   держал ровно это содержимое на момент одной из своих синхронизаций, его нынешняя запись — более новая.
   (Решение по ревью: «держал» накапливается у копии — `mirror_copies.held`, последние записи на путь, — а не только
   текущие состояния пар: иначе передача, переписавшая состояние X в одной паре, давала ложный конфликт с другой
   копией. Режим файла — часть записи: бит исполнения, поставленный в Y, не снимается молча);
4. иначе — «локальное изменение», замена только с подтверждением или «Оставить в копии».

Правило 3 убирает ложные конфликты основного сценария. Пример: день 1 — правка `f` на A, «Отправить во все»
(B и C получают версию A); день 2 — правка `f` на B, «Отправить во все». У пары B–C состояния нет или оно
старое, но `f` в C равна версии A, которую B держал после синхронизации с A в день 1, — C обновляется без
вопроса. Отставший A, отправляя в C правку, которой C получил от B и которой A никогда не держал, правило 3 не
проходит — защита из анти-цели сохраняется. Удалённый в Y файл (`y` нет) проверяется только правилом 2.

Нет состояния стороны (новая пара, перенос) и правило 3 не сработало — отличие считается «локальным
изменением»: осторожно, как сейчас у зеркала без базы.

### Схема и перенос (шаг 63)

Новые таблицы группы, копий и пар; `project_mirrors` **не удаляется и не меняется** — новый код его больше не
читает. Перенос в шаге:

- строки с одинаковыми `source` + `project` образуют одну группу (зеркала A→B и A→C — группа {A, B, C});
- копия назначения — из `destination`, `root`, `name_key`, `location` (`pid` пока неизвестен);
- копия источника — из `source` + `project` (`root` и имя пока неизвестны);
- пара источник–назначение: состояние назначения = прежний `baseline`, состояние источника — нет,
  время = `synced`;
- исключения группы — объединение исключений её строк (не больше `project_mirrors.EXCLUDE_MAX`: лишнее
  отбрасывается, в журнал — только число);
- две строки группы с одним компьютером назначения (разные папки) — обе остаются копиями группы.

Недостающее заполняется при работе, когда мост на связи:
- `pid` копии назначения — из ответа `mirror_destination` (он уже возвращает `pid`) при любом сравнении или
  открытии окна на этом компьютере;
- `root` и имя копии источника — из `mirror_identity` (мост с новой возможностью, ниже).

Если при заполнении выясняется, что две строки — одна папка (раньше владелец вручную сделал обратное зеркало
B→A), строки сливаются в одну (пары переводятся на оставшуюся; из двух пар с одной и той же второй копией
остаётся более поздняя по времени синхронизации), а их группы — в одну. Настройки при переносе и слиянии **не
удаляются** автоматически: две копии на одном компьютере, если так вышло, видны в окне, лишнюю владелец
отвязывает сам. Папки не трогаются никогда.

Откат: прежний код видит `project_mirrors` в состоянии на момент обновления (односторонние зеркала с прежними
базами); копий, добавленных новым кодом, и синхронизаций, сделанных им, не видит. Синхронизации прежнего кода
после возврата вперёд не учитываются (пары осторожнее — больше «локальных изменений»). SQL-обход не нужен.
Строка шага 63 — в таблицу отката `CLAUDE.md`; `manage.ENCRYPTED_BACKUP_FIELDS` (пункт `mirrors`) проверяет и
новые зашифрованные поля.

### Мост (новая возможность `hello.mirror_groups`, версия моста — следующая minor)

- `mirror_identity {project}` дополнительно возвращает `root` — id папки проектов, где лежит проект, и `folder` —
  её путь (как `mirror_destination`). Так копия-источник становится адресуемой как назначение.
- **SQLite.** В манифесте (`mirror.scan`, обе стороны):
  - `-wal`, `-shm`, `-journal` рядом с файлом-базой SQLite (заголовок `SQLite format 3\0`, как сейчас) — всегда
    «пропущен»: это служебные файлы, переносить их бессмысленно, а `-shm` открытой базы меняется постоянно;
  - сама база — «пропущен», если рядом **непустой** `-wal` или `-journal` (незакрытая база или брошенный журнал:
    файл базы без журнала был бы неполным); пустой журнал признаком открытой базы не считается;
  - отказа `busy` «обнаружена открытая база SQLite» больше нет;
  - соседей узнавать по уже прочитанному списку папки, без лишних обращений к диску на каждый файл.
- **Причина пропуска.** Если сервер просит (`reasons: true` в `mirror_scan` / `mirror_destination`), пропуск
  из-за базы приходит как `["skip", "sqlite", 0, 0]`; без флага — прежний `["skip", "", 0, 0]`, чтобы новый мост
  со старым сервером (откат) не получил «мост вернул неверный список файлов». Сервер принимает оба вида и
  везде, где сейчас сравнивает с `SKIP`, считает пропуском любой `kind == "skip"`.

Старый мост в группе: работает как назначение, если у его копии известны `root` и `pid`; базы SQLite на нём
по-прежнему валят сравнение (окно говорит «Обновите мост на компьютере …»). Добавление зеркала с компьютера
требует на нём `mirror_groups` (регистрация текущей копии). Мосты обновляются автоматически после выкладки.

### Сервер (`project_mirrors.py`)

Маршруты остаются под `/api/code/agents/{aid}/projects/{pid}/mirrors`; `{aid, pid}` — открытый проект, то есть
текущая копия, источник любой отправки.

- **Список** (без обращений к мостам — для индикатора): текущая копия (или её отсутствие), остальные копии
  группы с компьютером, папкой, «на связи», временем синхронизации **с текущей копией** (из пары), состоянием
  передачи, признаком `reenter`; исключения группы.
- **Добавить** — как сейчас (компьютер, папка проектов, имя или найденная копия); при первом зеркале проекта
  сервер регистрирует текущую копию (`mirror_identity` → `root`, имя). Выбранная папка F на компьютере Y:
  - F ни в какой группе — F входит в группу текущей копии (группа создаётся, если её не было);
  - F уже в группе G, у текущей копии группы нет — текущая копия **присоединяется к G** (это и есть «второй
    компьютер видит»: третий компьютер, привязав папку A, попадает в группу {A, B}, а не отрывает A от B).
    Если в G уже есть копия на этом же компьютере (проект переименован, прежняя папка), — подтверждение
    «заменить прежнюю копию этого компьютера» (`replace`, как сейчас `elsewhere`); прежняя строка снимается
    вместе с её парами;
  - F в другой группе G, у текущей копии своя группа G1 — группы **сливаются** в одну, если в них нет копий на
    одном и том же компьютере; иначе отказ с названием компьютеров («отвяжите лишнюю копию»);
  - F уже в группе текущей копии — отказ «уже зеркало этого проекта»;
  - на компьютере Y уже есть другая копия группы — отказ.
  «Найденные копии» помечают папку в чужой группе: «Копия в группе с <компьютеры>» и кнопкой «Присоединить»
  (или «Объединить»), чтобы владелец видел, с кем свяжется.
- **Сравнить / отправить / разница файла** — как сейчас, но для пары «текущая копия → выбранная копия»;
  токен плана включает пару и её время синхронизации. Отправка обновляет оба состояния пары.
- **Отвязать** — удаляет выбранную копию из группы (только настройки; папка остаётся). Осталась одна копия —
  группа удаляется вместе с ней (и с исключениями).
- **Исключения** — на группу; проверка `mirror_exclude` — у обоих мостов каждой сверяемой пары, как сейчас.
- **Поиск копий** — как сейчас, но не показывает компьютеры, уже имеющие копию в группе, и копии этой группы;
  копия другой группы — с `elsewhere`.
- Передачи: одна на компьютер назначения, всего не больше четырёх (`TRANSFERS`, как сейчас); прогресс — по паре.
- Права: `project_access.owner` на каждый задействованный компьютер; копия в папке, открытой другим
  пользователям, назначением не бывает (`_private_destination`).
- Журнал — только id и коды, как сейчас.

### Окно и кнопка (`project-mirrors.js`, `code.js`)

Кнопка: при открытии проекта страница берёт список (без мостов) и показывает цифру в правом верхнем углу
«Зеркала» — стиль как у счётчиков статус-бара (`.code-changed-count`), `aria-label` с числом копий; 0 — без
цифры. После закрытия окна цифра обновляется.

```
Зеркало · studio
  Копии на других компьютерах
  workstation-b      · E:\projects\studio     не на связи
  laptop   · C:\work\studio    синхронизирована с этим компьютером · 21.11 14:02     [Сравнить]
  workstation-a  · E:\projects\studio     ещё не синхронизировалась                               [Сравнить]

  [Отправить во все копии]   [+ Добавить зеркало]
  ▸ Постоянные исключения (2)

  (выбранная копия — нынешний вид сравнения: сводка, различия, «Оставить в копии»,
   [Обновить сравнение] [Отвязать копию] [Отправить изменения])
```

- Нет группы — окно сразу в режиме добавления (форма + «Найденные копии»), как сейчас без зеркал.
- «+ Добавить зеркало» открывает форму и «Найденные копии»; поиск по компьютерам запускается только здесь,
  а не при каждом открытии окна.
- «Сравнить» — нынешний вид сравнения для выбранной копии; кнопка отправки называется «Отправить изменения»
  (направление видно), «Скопировать весь проект» — когда папки копии ещё нет.
- **«Отправить во все копии»:** сравнивает текущий проект с каждой копией, которая на связи и открыта
  (компьютер без PIN открывается сам, как сейчас `unlock`); затем одно подтверждение со сводкой по копиям
  («workstation-b — 3 изменения, из них 1 удаление»). Копии со «своими» изменениями (локальные изменения в паре) в
  общую отправку **не входят** — строка помечена «есть изменения, которых нет здесь — откройте сравнение».
  Не на связи и требующие PIN — тоже пропускаются с пометкой (PIN вводится в строке копии). Прогресс — в
  строках копий.
- «Постоянные исключения» — на группу, видны всегда, когда группа есть (выход из нынешнего тупика).
- Пропуск с причиной `sqlite` в списке различий — «Пропущен · открытая база SQLite»; сводка пропусков
  упоминает открытые базы.
- Новые подписи — через `tr` с переводом в `static/en.js`; названия кнопок — в `docs/glossary.md`.

## Ограничения

- Содержимое файлов — только через канал и память сервера, как сейчас; в базе — только шифром.
- Схема — только добавлять (`db.STEPS`), прежний код обязан работать с новой базой.
- Сервер выкладывается раньше обновления мостов: новый сервер со старыми мостами работает (с ограничениями
  выше), новый мост со старым сервером — тоже (флаг `reasons`).
- Тесты — по правилам проекта: быстрые без реального времени и сети (`tests/fake_bridge.py` нужно научить
  новой возможности и причинам пропуска), браузерные — `integration`; набор моста — свой (`agent/`).

## Решения автора (владельцу — на проверку при чтении)

- Правило 3 «X уже держал это содержимое» — чтобы «Отправить во все» не спотыкалось о ложные конфликты.
- Состояние источника в паре не включает неприменённые пути (оставленные в копии, пропущенные, исключённые).
- Присоединение к существующей группе и слияние групп при привязке папки; без автоматического удаления
  настроек при переносе.
- «Отправить во все» пропускает копии со своими изменениями, не на связи и требующие PIN — с пометкой.
- Поиск копий — только по «+ Добавить зеркало», не при каждом открытии окна.
- Служебные файлы SQLite пропускаются всегда; база — только при непустом журнале.
- Отвязка последней второй копии удаляет группу вместе с исключениями.
